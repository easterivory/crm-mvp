# SEPARATE POSTBACK SERVER ONLY: памятка для следующего диалога

Цель: развернуть ТОЛЬКО отдельный приёмник из `postback_gateway/`. Не разворачивать вторую CRM. Не запускать корневые compose/deploy-dev.sh, миграции, сиды или Telegram workers. Не копировать `.env` CRM, её базу, Redis, токены ботов и сессии аккаунтов.

## Протокол 2 — порядок обновления (04.11.2026)

Сначала другой диалог обновляет основную CRM до миграции 0094 и jobs worker,
потом этот диалог обновляет только gateway. Новый manifest имеет version=1 для
совместимости и protocol_version=2; список endpoints содержит frozen revision
и необязательный текст ACK. Старые очереди/instance_id сохраняются в том же volume.
Gateway записывает received_at и endpoint revision в принятый конверт, отправляет
подписанный heartbeat. При старой CRM v1 эти гарантии отсутствуют: проверить
protocol_version до перевода трафика. Не выдавать режим v1 за полностью обновлённый.

Синхронизация каждые ~30 сек. При устаревшем manifest новый приём прекращается;
старые задания остаются. Иммутабельные UUID/тело не менять при retry/restore.
Секретный URL настраивается и копируется в CRM: Настройки → Партнёры → Получение
постбэков. Настройки домена/VPN/ключа на этом сервере — только инфраструктура.
Исходящая отправка покупателю НЕ переносится сюда этим пакетом.

Обычный ответ — JSON accepted + delivery_id. Если CRM настроила статический ACK
(например OK), он возвращается только после сохранения на диск. Проверьте, что
партнёр повторяет 429/503. Gateway поддерживает JSON object и URL-encoded form,
НЕ multipart. Старую интеграцию с multipart нельзя переводить без смены формата.

Состояния ambiguous/invalid/conflict/stale от CRM — доставленные терминальные
бизнес-результаты, а не повод слепо повторять запрос. Причину техник разбирает в
CRM. Только сетевые/серверные сбои повторяются автоматически.

Новая обычная ротация имеет grace period (обычно 3600 сек). Аварийный отзыв или
архивирование может остановить pending: согласовать с основным сервером и сохранить
dead для разбора. Создание нового endpoint не отключает старые адреса автоматически.

Локальные PostgreSQL/Redis и реальные проверки перезапуска процесса выполнены
при разработке; образ контейнера и сеть ваших двух серверов всё равно нужно
проверить при развёртывании. Docker Desktop в среде разработки недоступен.

Передать в диалог этот документ и папку `postback_gateway/` целиком (включая `.env.example`, Dockerfile, compose, nginx example и AGENTS.md). Бизнес-настройки остаются в CRM, локально их дублировать не нужно.

## Данные для согласования

- Домен приёмника, DNS и доступ к сертификату TLS.
- VPN-адрес основного сервера, адрес приёмника, служебный порт CRM (примеры `10.77.0.1:8099` и `10.77.0.2`).
- Отдельный общий секрет HMAC, согласованный с основным сервером. Минимум 32 случайных символа, рекомендуется `openssl rand -hex 32`. Не передавать открыто в чате.
- Какие проекты разрешены (настраиваются на основном сервере), объёмы событий и требования партнёров к ответу.

## Подготовка хоста

1. Установить Docker Compose, nginx, WireGuard, настроить синхронизацию времени. Выделить диск для постоянной очереди и защищённых бэкапов; размер зависит от потока и максимального времени простоя CRM.
2. Поднять VPN до основного сервера. Проверить доступ из контейнера к нужному VPN IP/порту. Не давать приёмнику доступ ко всей сети CRM. Не отключать firewall ради Docker; проверить правила forwarding/DOCKER-USER.
3. Скопировать ТОЛЬКО `postback_gateway/` в отдельный каталог (например `/opt/postback-gateway`). Build context — этот каталог. Создать `.env` по примеру с правами 600.
4. Запустить `docker compose -f compose.gateway.yml up -d --build`. Контейнер работает непривилегированным пользователем, с read-only корнем; постоянный named volume содержит SQLite. Порт 9080 опубликован только на loopback.
5. Проверить `docker compose -f compose.gateway.yml exec gateway python -m postback_gateway.admin stats`. Возраст manifest должен появиться и обновляться каждые ~30 секунд. Если нет — проверить ключи, время, маршруты, firewall и разрешённые проекты. Не выводить секреты в логи.
6. Настроить HTTPS nginx по `nginx.gateway.conf.example`, заменив домен/сертификаты. Проверить `nginx -t`, затем reload. Из интернета доступны только `/pb/<secret>` по HTTPS. Служебные пути, Swagger и панель CRM не публикуются.
7. По возможности включить DDoS/WAF-защиту у DNS/CDN-провайдера. Для callback-пути не использовать JavaScript challenge/CAPTCHA и кэширование. При CDN отдельно настроить доверенные адреса real-IP: нельзя доверять произвольному X-Forwarded-For. Подстроить лимиты под согласованный трафик партнёров, не выключать их глобально.
8. Smoke-test только на согласованном тестовом endpoint/лиде. После успеха попросить диалог основного сервера указать новый PUBLIC_BASE_URL и переводить партнёров постепенно.

## Поведение и пределы

- GET/query, POST JSON object, POST application/x-www-form-urlencoded. Multipart/files и неизвестные типы отвергаются 415. Тело до 64 КиБ, query до 8 КиБ, до 100 полей query/form. Проверить формат каждого партнёра до перевода.
- Ответ `200 {"status":"accepted","delivery_id":"..."}` означает запись на диск. Не обещает, что лид найден. При переполнении/сбое диска/устаревшем manifest — 503, при лимитах nginx — 429. Партнёр должен уметь повторять такие запросы. Не подменять их фиктивным 200.
- Передача в CRM последовательная, по умолчанию не более 5 событий/сек плюс время запроса. Это сознательный предел, защищающий основной сервер; повышать только после измерений.
- Список активных секретов кэшируется максимум 5 минут. При длительной недоступности CRM новые запросы прекращают приниматься, но ранее принятые не теряются. Это защита от неограниченного использования отозванных адресов. Значение TTL ограничено 30–3600 сек; увеличение ослабляет отзыв секретов.
- У сетевых ошибок/5xx/429/проблем авторизации повтор с увеличивающейся задержкой; ID и байты события неизменны. Перенаправления не выполняются. 400/404/409/413/422 переводят запись в dead, не удаляют.
- Ответ CRM `unmatched` — доставленная, но не сопоставленная запись. Нужно исправлять параметры/данные через CRM, не бесконечно повторять её.
- Защита транспортного повтора работает даже после commit CRM и потери HTTP-ответа. Повторная НОВАЯ отправка самого партнёра имеет другой delivery_id; для неё нужен уникальный ID события в настройках CRM. Нельзя безусловно объединять одинаковые суммы/тела: это могут быть разные реальные события.

## Обслуживание

Команды перечислены в README папки. Настроить мониторинг `stats` хотя бы раз в минуту: stale manifest, dead>0, растущий возраст pending, близость к лимиту очереди, свободное место и перезапуски контейнера. Один `/health` не проверяет доставку.

Резервировать очередь через SQLite backup API (`admin backup`), не копировать только основной файл живой WAL-базы. Бэкап содержит секреты endpoint и данные постбэков; хранить шифрованно вне хоста. Согласовать восстановление с основным сервером, не удалять его журнал дедупликации.

Запрещено `docker compose down -v` при очереди, массовый retry с новыми ID, удаление pending/dead для освобождения места, публикация SQLite/бэкапов/`.env` в веб-каталог. Успешные локальные записи очищаются через 7 дней; остальные только вручную после разбора. Диск и очередь не бесконечны, отказ диска без актуального бэкапа остаётся риском.

Секрет интеграции и endpoint-секреты — разные вещи. Ротацию общего секрета проводить согласованно на обоих серверах; на время несовпадения доставка повторяется, manifest стареет. Не выполнять автоматическую ротацию при установке.

## Границы защиты

Это отдельная точка приёма и ограниченная очередь, не гарантия от любых атак и не средство полного сокрытия CRM. Взлом gateway раскрывает секреты принятых endpoint и может позволить подделывать события этих endpoint. На нём нет токенов ботов, доступа к БД или всей CRM; именно поэтому сеть и права должны быть ограничены. Подписи партнёров специфичны для провайдера и в этой версии дополнительно не проверяются: вход аутентифицируется секретом адреса, транспорт gateway→CRM подписан HMAC.
