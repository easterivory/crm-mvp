# Проверка рекламного обновления, 1 ноября 2026

Проверка выполнена локально. Рабочий сервер и рабочая база не изменялись. PostgreSQL и Redis для проверок отдельные; реальные рекламные отправки не выполнялись.

## Исправленные риски

- Повторная проверка защиты перед отправкой могла возвращать устаревшие ORM-объекты. Конфигурация, проект, бот, статус лида и попытка доставки перечитываются; добавлены проверки изменения настроек/тегов между фиксацией попытки и сетевым запросом.
- Пользовательская команда могла перезаписать рекламную паузу. Проверяется самостоятельная запись рекламного участия, а не только флаг в состоянии воронки. Закрыт обход через старый движок и его кнопки.
- Ручной сброс диалога не отменял рекламную очередь. Теперь сброс сериализован блокировкой чата и отменяет старое участие. При возврате явно выполняется flush: производственная сессия не использует autoflush, и уникальный ключ должен освободиться до создания нового цикла.
- Telegram 429 ошибочно попадал в неопределённые доставки. Явный отказ по лимиту откладывает тот же слот на retry_after. Неопределённый таймаут по-прежнему не повторяется автоматически.
- Ошибка или длительная блокировка прогона старой базы могла остановить обработку слотов. Транзакция порции откатывается отдельно, обработка слотов продолжается; ожидание блокировок рекламного обработчика ограничено.
- Выключение слота после начала подготовки отправки дополнительно проверяется перед Telegram. Уже начавшийся сетевой запрос отозвать невозможно.
- При одинаковых позициях порядок в UI и в очереди различался. Теперь используется одинаковый порядок position/id.
- Некорректная структура содержимого слота возвращает ошибку валидации вместо случайной серверной ошибки.
- Скрипт deploy-dev.sh запускал новый код до миграции. Теперь сначала собираются образы, затем останавливаются обработчики, создаётся дамп, выполняется миграция и запускается новый код. Ошибка сборки не останавливает прежнее приложение; ошибка бэкапа/миграции не запускает новое.
- Резервные копии закрыты правами доступа и исключены из Git/Docker-контекста. Файлы медиа и ключи шифрования резервируются отдельно.

## Что проверено

- Общие автоматические тесты приложения и production-сборка frontend.
- Реальная PostgreSQL: миграция поверх текущей схемы, имитация сбоя посередине миграции с полным откатом DDL, сохранность прежнего проекта.
- Создание pg_dump и восстановление через pg_restore в другую тестовую БД: сохранены прежние карточки и новые рекламные настройки/очереди.
- Защитные теги, целевые статусы, выключенный проект/сценарий, удаление бота из выбора, отсутствие слотов, изменение содержимого и защита от повторной отправки.
- Два обработчика одного участника; изменение защиты после фиксации попытки; отмена старого участия перед повторным запуском.
- Права менеджера/администратора и запрет редактирования чужого проекта через API.
- Явные отказы Telegram и неопределённый результат, подтверждение старой базы, конфликт версий редактора.
- Совместимость с рассылками, повторным /start через 30 дней, ручным перехватом, отложенными заданиями и механизмом доставки инфобота.
- Отдельные Redis: аварийное завершение, перезапуск и восстановление очереди. Эти тесты не перезапускают сервер CRM.
- Desktop/mobile: сохранение слота, подтверждение старой базы, открытие отчёта. API браузерного теста подменён.
- Скрипт выкладки проверен с подменёнными командами: успешный путь, ошибка сборки, бэкапа и миграции. Настоящие SSH, Git reset и Docker deploy не запускались.

## Остаточные ограничения

Это не доказательство отсутствия всех ошибок. Проверки восстановления выполнялись на синтетической тестовой базе, не на свежем бэкапе production. Полноценного нагрузочного прогона всей CRM на параметрах рабочего сервера и живой проверки рекламы через Telegram не было.

SQL-бэкап не включает медиа и внешние секреты. Локальная копия на том же сервере не защищает от потери диска. Перед обновлением нужна независимая копия и проверенные ключи восстановления.

При неоднозначном сетевом результате возможен пропуск поста вместо дубля. При изменении защиты во время уже выполняющегося сетевого запроса одно сообщение может завершить отправку. Откат приложения после рабочих рекламных прогонов требует отдельного плана: старый код не понимает рекламные состояния.

Полная старая цепочка миграций с нуля имеет отдельную проблему в 0012 (повторный waiting_for_answer); в этом обновлении проверяется переход текущей схемы на 0090. Скрипт deploy-dev.sh предназначен для dev и сохраняет прежнюю привязку к ветке/каталогу; не запускать его на другом окружении без адаптации.

## Рекомендуемый запуск

Свежая независимая копия БД, медиа и секретов → миграция до нового API/worker → обновление с выключенными сценариями → тестовый бот → ограниченный проект → остальные проекты. Прогон старой базы только после проверки списка исключений и подтверждения администратора.
