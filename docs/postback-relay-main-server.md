# MAIN CRM SERVER ONLY: интеграция приёмника постбэков

Этот документ для диалога, обслуживающего ОСНОВНОЙ сервер. Приёмник разворачивается на другом хосте. Не запускать `postback_gateway/compose.gateway.yml` и не устанавливать его публичный nginx на сервер CRM. Корневые compose и deploy-скрипты не добавляют приёмник; основной Docker-образ исключает его папку.

## Что входит в обновление CRM

- Миграция `20261102_0092` после `0091`: только новая таблица `postback_relay_deliveries`. Старые таблицы и данные не переписываются.
- Два служебных маршрута: `GET /internal/postback-relay/manifest` и `POST /internal/postback-relay/deliver`. По умолчанию выключены и отвечают 404.
- HMAC-SHA256 по методу, пути, времени и хешу тела; допустимое расхождение времени 60 секунд. Проекты ограничены явным списком.
- Доставка имеет UUID. Одна транзакция фиксирует обработку события и результат доставки. Повтор того же ID/тела возвращает прежний результат; изменение тела с тем же ID отклоняется. HTTP 200 выдаётся после commit.
- Существующие настройки постбэков в CRM остаются источником истины: URL, сопоставление параметров, тип события, включение, ротация секрета. Внешний сервер получает только хеши активных секретов выбранных активных проектов, без базы лидов и токенов Telegram.

## Порядок подготовки

1. Проверить актуальный бэкап и ревизию миграций. Обновить код, применить `alembic upgrade head`. Не удалять старые данные при ошибке. Сначала оставить интеграцию выключенной.
2. Согласовать с диалогом второго сервера VPN-адреса и сгенерировать отдельный общий секрет (`openssl rand -hex 32`). Не использовать SECRET_KEY CRM или токены ботов. Передать по защищённому каналу, не публиковать в переписке/логах.
3. Настроить WireGuard. Пример адресов: основной `10.77.0.1`, приёмник `10.77.0.2`. Это примеры, проверить конфликты сетей.
4. Разрешить приёмнику доступ ТОЛЬКО к служебному HTTP-порту на VPN-интерфейсе (пример 8099). Не открывать PostgreSQL, Redis, SSH или весь API для этого peer. VPN сам по себе не задаёт ограничения firewall.
5. Поднять отдельный nginx listener на VPN IP с конфигурацией ниже. В публичных server-блоках CRM добавить `location ^~ /internal/postback-relay/ { return 404; }`. Проверить, что публичные Docker-порты не позволяют обойти nginx/firewall. Не ломать действующие webhooks и лендинги глобальным закрытием всех портов.
6. Добавить переменные ТОЛЬКО в `.env` основного сервера:

```dotenv
POSTBACK_RELAY_ENABLED=true
POSTBACK_RELAY_SECRET=<отдельный общий секрет минимум 32 символа>
POSTBACK_RELAY_PROJECT_IDS=<UUID проекта,UUID второго проекта>
POSTBACK_PUBLIC_BASE_URL=
POSTBACK_DIRECT_ENABLED=true
```

Пустой список проектов запрещает все проекты. `*` открывает все проекты приёмнику, использовать только осознанно. Не менять общий `BASE_URL`: он используется другими частями CRM. Сначала оставить PUBLIC_BASE_URL пустым: ссылки в CRM останутся прежними, пока второй сервер не готов.

7. Перезапустить API с новыми переменными. Согласовать успешную синхронизацию manifest со вторым диалогом.
8. Выполнить согласованный smoke-test на отдельном тестовом проекте/лиде. Проверить один постбэк, повтор доставки после потери ответа, отображение квитанции в CRM и отсутствие дубля события. Не создавать тестовые депозиты реальным лидам.
9. Только после проверки записать `POSTBACK_PUBLIC_BASE_URL=https://postbacks.example.com` и перезапустить API. В CRM новые/существующие ссылки выбранных проектов будут показывать этот домен и отметку «Внешний приёмник». Сам секрет и настроенные поля не меняются.

## Пример VPN listener nginx (основной сервер)

Заменить адрес/порт backend на реальные из существующей установки. Эта конфигурация не заменяет публичный виртуальный хост CRM.

```nginx
server {
    listen 10.77.0.1:8099;
    server_name _;
    client_max_body_size 256k;
    client_body_timeout 10s;
    location ^~ /internal/postback-relay/ {
        allow 10.77.0.2;
        deny all;
        proxy_pass http://127.0.0.1:8000;
        proxy_connect_timeout 3s;
        proxy_read_timeout 25s;
        proxy_next_upstream off;
    }
    location / { return 404; }
}
```

Если используете Cloudflare для публичной CRM, закрыть обход напрямую через исходный IP с сохранением необходимых интеграций. Сам перенос постбэков не скрывает IP, который раскрывают другие домены/DNS/сервисы.

## Совместимость и откат

- Старые `/pb/<secret>` продолжают работать, пока `POSTBACK_DIRECT_ENABLED=true`. Это облегчает постепенный переход, но оставляет старый вход открытым. После перевода ВСЕХ проектов/партнёров его можно выключить. Настройка глобальная, не выключать при частичном переносе.
- Отключение endpoint/ротация секрета применяется в CRM немедленно; на приёмнике список обновляется за 30 секунд. Уже принятые под старым секретом, но ещё не обработанные события могут попасть в dead с HTTP 404. Перед ротацией лучше дождаться пустой очереди; не делать это автоматически.
- Отключение relay не удаляет его очередь. Сначала остановить внешний приём и согласовать дренирование/переход с партнёрами, затем выключать интеграцию.
- Не удалять `postback_relay_deliveries`: это защита от повторов, в том числе при восстановлении старого бэкапа очереди. Downgrade миграции намеренно запрещён. Обычный бэкап PostgreSQL включает таблицу.
- Свежий бэкап CRM и бэкап приёмника согласовывать по времени. Восстановление старой базы CRM без восстановления/сверки доставки может потерять уже подтверждённые события; точка восстановления требует отдельного плана.

## Работа техника в CRM

В настройках интеграции партнёра используется существующая панель постбэков: создать endpoint, выбрать тип события, указать параметры идентификатора/суммы/валюты/внешнего ID события, скопировать ссылку. Рекомендуется точный `lead_id` и уникальный ID события партнёра. `tracking_code` обозначает источник, а не уникального человека; прежняя логика такого сопоставления этим апдейтом не меняется.

Журнал квитанций в CRM показывает ДОСТАВЛЕННЫЕ события (`processed`, `duplicate`, `unmatched`). Ещё ожидающие передачи находятся в очереди приёмника, не в этом журнале. `unmatched` означает доставку без сопоставления лида и не повторяется автоматически.

Никаких сервисов приёмника в корневой compose добавлять не надо.
