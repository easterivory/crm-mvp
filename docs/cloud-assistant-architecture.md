# ADR: реализация cloud assistant V1

Дата: 07.11.2026. Цель: сохранить стек существующей CRM и сильную границу согласования.

## Протокол и зависимости

В основном приложении добавлен только OAuthLib 3.3.1. Он проверяет authorization
code/refresh flow и PKCE, приложение хранит состояние в PostgreSQL. Нового IdP,
платного сервиса, OpenAI API key или постоянного LLM-процесса на CRM нет.

Access/refresh tokens opaque, а не JWT: resource/issuer/scopes привязаны к записи
подключения, токены ищутся по SHA-256 и проверяются сервером на каждом запросе.
Это OAuth resource-server validation через серверное состояние, не пропуск
signature check. Ключи существующих CRM login JWT не переиспользуются.
TTL access — 10 минут, code — 60 секунд, refresh family — максимум 7 дней.
Повтор использованного refresh отзывает подключение. Только authorization code
с S256 и refresh grants; без password/client-credentials/implicit grants.

На первом этапе используются заранее зарегистрированные клиенты. DCR/CIMD
и загрузка произвольных metadata URL не реализованы и не рекламируются discovery.
Это убирает отдельную поверхность SSRF и не требует новой инфраструктуры IdP.
Совместимость static client/callback должна быть подтверждена настоящим целевым
ChatGPT-клиентом; если там нужен другой режим — это отдельная согласованная доработка.

MCP SDK 1.26.0 требует Pydantic >=2.11, а CRM использует 2.7. Поэтому адаптер
`assistant_bridge/` — отдельный Docker context/venv с закреплёнными зависимостями,
не обновляет FastAPI/Pydantic/HTTPX работающего приложения. Transport:
Streamable HTTP, stateless, JSON response. По этому пути можно обращаться из
облака без Computer Use или включённого компьютера пользователя.

## Применение и совместимость

MCP только читает и готовит заявки. Approve-and-apply — другой native API с
CRM login JWT, проверкой Origin, прав, plan hash, TTL и сохранённых зависимостей.
Модель не получает разрешение approve и не может эмулировать его аргументом.

Подтверждение+запись+AuditLog — одна транзакция; business work внутри savepoint.
Успешный результат сохраняется в заявке. Повтор возвращает его, не повторяет
создание сущностей. Отдельный idempotency header для approve не нужен: ключ —
неизменяемый proposal_id, а hash фиксирует состав изменений.

В первой версии не исполняются внешние эффекты, не поддерживаются cross-project
планы и ссылки на новые ресурсы другой операции. Максимум 5 явно перечисленных
операций; бизнес-сервис создания оффера сам создаёт связанный выключенный endpoint.
Создание невалидной заявки возвращает типизированную ошибку до сохранения, а не
сохраняет заведомо неприменимый draft. Pending план меняется только заменой заявки.

Для изменения standalone endpoint требуется доказанная история отсутствия
активности. Старый журнал не сохранял факт is_active, поэтому новая добавочная
колонка ever_active=true трактует legacy как unknown. Новые выключенные endpoints
явно получают false, активация навсегда ставит true. Проверяется также marker
нового snapshot: после работы старого кода неизвестную ревизию не считаем безопасной.
Старые callback, события, dedup и выдачи ссылок не меняются.

Назначение оффера у черновика вынесено из router в общий небольшой валидатор;
семантика старого маршрута сохранена. Остальные существующие business services
переиспользуются, не заменяются новой реализацией трекинга или постбэков.

## Данные и ресурсы

Для облака используются отдельные allowlist DTO. Полные URLs и secret tokens
административных endpoints не проксируются. Частные ссылки вводятся через native
UI и шифруются отдельным Fernet key; в plan/tool outputs остаётся opaque reference.
Просмотр исходной ссылки — отдельный native UI request, не MCP tool.

Отчёты возвращают прежнюю методику/фактический UTC диапазон, признаются неполными,
не подменяют отсутствующие события подтверждённым нулём. Финансовые выплаты
исключены. Lead summary требует отдельного scope и не выдаёт переписку/контакты.
Кэш отчёта — максимум 30 секунд в отдельном Redis namespace. Ключ включает
владельца, connection, актуальные scopes/policy, состояние проекта и все фильтры.
Доступ проверяется до чтения кэша; generated_at показывает время самого расчёта.
Недоступный кэш означает miss, но не снимает обязательный общий limiter.

Ассистент использует lazy отдельный SQL pool (2, overflow 0), локальные query/lock
timeouts и Redis namespace для общих лимитов/leases. При отказе limiter доступ
закрывается. В адаптере нет БД/Redis credentials. Совместная нагрузка на большой
production-копии остаётся обязательным deployment gate, а не гарантией из unit tests.

Модуль opt-in на MAIN-сервере; gateway не задействован. Никаких автоматических
миграций, публикаций, включений трафика или изменений секретов при импорте модуля.
