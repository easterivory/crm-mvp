# Облачный помощник: передача отдельному диалогу настройки

**Только основной сервер CRM.** Этот файл не является разрешением на выкладку.
Код подготовлен локально, модуль по умолчанию выключен. Развёртывание, домен,
добавление OAuth-клиента и подключение production-данных согласует пользователь.
Сервер постбэков и `postback_gateway/` для этого не используются и не меняются.

ТЗ: `docs/cloud-crm-assistant-spec.md`. Решения и границы реализации:
`docs/cloud-assistant-architecture.md`.

## 1. Что реализовано

- Отдельные scoped OAuth-подключения выбранного superadmin к выбранным проектам.
- Read tools: каталог, безопасные настройки, трекинг по прежней методике,
  диагностика, ограниченная карточка при отдельном scope, postback dry-run.
- Заявки на изменения. Чат не получает approve/apply, deploy, send, SQL или shell.
- Подтверждение конкретного hash в авторизованной CRM, проверка зависимостей,
  атомарная запись и сохранённый идемпотентный результат.
- Офферы/приём создаются выключенными; выбор оффера возможен только у черновика.
- Партнёрский URL вводится в защищённой форме CRM, модель получает только ID.
- Отдельный stateless MCP-адаптер на официальном Python SDK, без CRM credentials.
- Вкладка «Настройки -> Облачный помощник» и раздел в документации CRM.

Код НЕ управляет кабинетом RioAff, не угадывает макросы Alanbase, не открывает
nginx `/pb/`, не включает endpoints и не запускает конверсии. Это отдельные задачи.

## 2. Что запросить до любых изменений

1. Разрешение пользователя на конкретную выкладку и подключение облачного клиента.
2. Текущие ревизии CRM/миграций, набор compose overrides и имя compose-проекта.
3. Отдельный HTTPS hostname помощника. Не переиспользовать ingress приёмника постбэков.
4. UUID пользователя пилота, UUID разрешённых проектов. Названия не заменяют UUID.
5. Реальную доступность custom MCP plugin в нужном аккаунте/workspace ChatGPT.
6. Client ID и точный redirect URI, показанные целевым MCP/OAuth-клиентом.
   Не брать callback из случайного примера; схемы callback меняются между клиентами.
7. Перечень согласованных scopes. Lead summary и preparation не выдавать по умолчанию.

Не передавать в этот или другой чат `.env`, bot tokens, Telegram sessions,
OAuth/refresh tokens, пароль БД, relay secret и исходную конфиденциальную ссылку.
Секреты остаются в утверждённом хранилище на сервере/в настройках клиента.

## 3. Совместимость и миграция

Новый head: `20261107_0098` после `20261106_0097`.

Миграция добавляет пять таблиц `assistant_*` и поле
`postback_endpoints.ever_active` с консервативным default=true для старых записей.
Старые события, лиды, чаты, очереди, callback secrets и активность не переписываются.
Положительный флаг означает «активность была или её история неизвестна»; он
используется только для запрета небезопасного облачного редактирования.

Новые выключенные endpoints, созданные новым сервисом, имеют ever_active=false.
После активации флаг остаётся true. Новые snapshots содержат
activity_history_version=1. Если endpoint менялся старым кодом после rollback и
этой отметки у его текущей ревизии нет, помощник также запрещает редактирование.
Сама обработка старых постбэков от этого не меняется.

Перед выкладкой: свежий бэкап, restore на отдельной БД, upgrade на копии,
сверка старых данных. Сначала миграция, затем API и обработчики одной ревизии.
Даже при выключенном помощнике новый ORM ожидает колонку ever_active.
Не запускать миграцию на gateway. Не удалять историю для «исправления» ошибки.

Root Docker build не включает `assistant_bridge/`. Корневой compose не запускает
MCP. Отдельный override подключается только по явному решению.

## 4. Переменные основного CRM

Все значения ниже — образец, не настройки действующего сервера:

```dotenv
ASSISTANT_ENABLED=false
ASSISTANT_MCP_ENABLED=false
ASSISTANT_CHANGES_ENABLED=false
ASSISTANT_ALLOWED_USER_IDS=<UUID одного согласованного superadmin>
ASSISTANT_ALLOWED_PROJECT_IDS=<UUID одного согласованного проекта>
ASSISTANT_MCP_RESOURCE_URL=https://assistant.example.org/mcp
ASSISTANT_OAUTH_CLIENTS_JSON='{"chatgpt-pilot":{"redirect_uris":["https://<точный-разрешённый-callback>"]}}'
ASSISTANT_INPUT_KEY=<отдельный Fernet key>
```

BASE_URL самой CRM должен оставаться её существующим каноническим HTTPS URL.
Не менять его на домен помощника. OAuth issuer:
`<BASE_URL>/assistant-oauth`. Empty allowlist запрещает всех/все проекты;
`*` в этой реализации не поддерживается.

ASSISTANT_INPUT_KEY создаётся как Fernet.generate_key() готовой библиотекой
cryptography. Это отдельный ключ, НЕ SECRET_KEY CRM и не ключ другого компонента.
Сохранить его резервную копию в защищённом хранилище: без него старые защищённые
inputs не расшифровать. Старые заявки в этом случае не применять вслепую.

OAuth-клиенты только заранее зарегистрированные, без сетевого DCR/CIMD lookup.
Поддержан публичный client с PKCE; для confidential client указать secret_sha256
в объекте клиента, а сам secret — только в интерфейсе клиента. Поддерживается
client_secret_basic, не client_secret_post. Пароли пользователя в MCP не передаются.
Статический client ID/redirect и способ authentication должны быть реально
проверены в выбранном облачном клиенте. Если он требует иной способ, остановиться
и согласовать адаптацию; не отключать авторизацию ради запуска.

## 5. Адреса и reverse proxy

На CRM, с обычным OAuth-контролем и без кэширования:

- `GET /assistant-oauth/.well-known/oauth-authorization-server`;
- `GET /.well-known/oauth-authorization-server/assistant-oauth`;
- `GET /assistant-oauth/authorize`;
- `POST /assistant-oauth/token`.

На отдельном hostname помощника проксировать только:

- `/mcp`;
- `/.well-known/oauth-protected-resource/mcp`.

Они идут к loopback `127.0.0.1:8114` отдельного MCP-контейнера, не к основному
API напрямую. Сохранить Host публичного hostname; TLS корректно завершается на
доверенном proxy. Не ставить интерактивный challenge/cache на OAuth/MCP.
Ограничить размер запроса 64 KiB, добавить nginx rate limiting и no-store для
OAuth-ответов. Не журналировать Authorization, query authorize/code или тела tools.

Статический adapter upstream: `http://api:8000/api/v1/assistant` внутри действующей
compose-сети. `/session`, `/tool-schemas`, `/tools/*` требуют opaque OAuth-токен;
их не подменять обычным административным JWT. UI endpoints принимают только
обычный CRM login и проверяют Origin. Не открывать БД/Redis ради помощника.

Не копировать полный `.env` в контейнер адаптера. Ему достаточно трёх адресов:
ASSISTANT_CRM_API_URL, ASSISTANT_MCP_RESOURCE_URL, ASSISTANT_OAUTH_ISSUER_URL.

## 6. Opt-in запуск после отдельного разрешения

Сохранить ТОТ ЖЕ набор существующих compose файлов/профилей и project name.
Ниже показан только добавляемый файл/профиль, не готовая универсальная команда:

```text
-f docker-compose.assistant.yml --profile assistant
```

Адаптер не имеет volumes, SQL/Redis credentials и Docker socket, запускается не
от root, с read_only filesystem, ограничениями RAM/CPU и loopback port.
При пустых/некорректных адресах его app factory откажется стартовать.
На сервере до старта проверить располагаемые RAM/CPU и общий DB connection budget.

Порядок включения: ASSISTANT_ENABLED -> ASSISTANT_MCP_ENABLED -> read-only тест
одного пользователя/проекта -> только после отдельного согласования
ASSISTANT_CHANGES_ENABLED. Последний флаг разрешает preparation/apply заявок,
НЕ даёт чату самостоятельного применения и НЕ включает живые постбэки.

## 7. Подключение ChatGPT и пользовательский сценарий

1. Добавить custom MCP plugin с Server URL, соответствующим ресурсу `/mcp`.
2. Выбрать OAuth, настроить согласованный клиент и точные callback/scopes.
3. Выполнить login обычным способом CRM. Вкладка «Облачный помощник» покажет
   client ID, scopes и выбор конкретных проектов. Не выбирать все автоматически.
4. Сначала запросить доступ и каталог. Убедиться, что чужие проекты недоступны.
5. Проверить отзыв подключения: следующий запрос должен быть отвергнут.
6. Переподключить только после согласования, перейти к QA-заявке.

Пример поручения после выдачи preparation scope:

> Прочитай настройки проекта <UUID>, ничего не применяй. Подготовь выключенный
> оффер RioAff по согласованным макросам. Исходную ссылку возьми из secure_input_ref
> <ID из CRM>. Никаких активаций, публикаций и тестовых конверсий.

Подготовка требует request_id. При потере ответа повторяется тот же request_id
с тем же содержимым; с другим содержимым он даёт conflict. Не генерировать новый
ключ, чтобы «продавить» неизвестный результат.

Модель получает approval URL. Пользователь проверяет в CRM проект, diff и
исходный адрес, затем подтверждает. Хеш плана отправляется native UI; ID самой
заявки является ключом идемпотентности approve. Не добавлять в запрос `confirmed`
или произвольный patch. Native API примера:

```http
POST /api/v1/assistant/proposals/<UUID>/approve-and-apply
Authorization: Bearer <обычный CRM login token; не передавать модели>
Origin: <канонический origin CRM>
Content-Type: application/json

{"expected_plan_hash":"<hash именно показанного плана>"}
```

Этот пример описывает UI-контракт, а не разрешает вызывать approve из CLI/чата.
При TTL 30 минут, изменившейся зависимости или недействующем подключении
не повторять старую заявку: подготовить новую с новым подтверждением.

## 8. Что обязательно проверить до production-готовности

- Настоящий облачный клиент: discovery, PKCE, callback/issuer, refresh, отзыв;
  локальный официальный MCP SDK не заменяет тест ChatGPT конкретного workspace.
- Все flags выключены: обычная CRM и прежние интеграции работают.
- Read-only pilot: никаких заявок/бизнес-записей от запросов статистики.
- QA-план -> явное согласование -> один результат при повторе запроса.
- Новый оффер и endpoint остаются выключенными, текущая воронка не меняется.
- Секретные URL/поля не выходят в tool outputs, ошибки и access logs.
- Миграция на полной копии, ограничения CPU/RAM/DB и реальные метрики API.
- Результаты baseline/нагрузки не хуже согласованного порога из ТЗ. Без замера
  на репрезентативной копии не обещать отсутствие влияния на production.

Локальные проверки разработчика: `tests/test_cloud_assistant.py`, общий pytest,
`assistant_bridge/contract_checks.py` в отдельном venv, TypeScript/build и
`frontend/tests/run-cloud-assistant.mjs` на 390/1440px.
Протокол и воспроизводимые команды: `docs/cloud-assistant-qa.md`.

## 9. Отключение и отказ

- Для немедленного запрета изменений выключить ASSISTANT_CHANGES_ENABLED.
- Для полного отключения — ASSISTANT_ENABLED=false и остановка только адаптера
  по отдельному согласованию. Не останавливать всю CRM и не удалять её volumes.
- Отозвать отдельное подключение можно из UI; токены больше не принимаются.
- Не удалять таблицы assistant_* и аудит при откате кода. Pending заявки сохранять,
  но не выполнять старой версией обработчика. Downgrade намеренно запрещён.
- Редактирование legacy endpoints с неизвестной историей не разблокировать SQL.
- Не менять POSTBACK_PUBLIC_BASE_URL, gateway nginx и relay allowlist в рамках
  подключения помощника. Получение RioAff и облачный доступ — разные интеграции.

## 10. Формат отчёта от диалога настройки

Сообщить без секретов: ревизию/миграцию, flags, hostname/issuer, вид OAuth-клиента,
доступные scopes/проекты, результаты облачного теста и revocation, состояние
адаптера и бюджеты ресурсов. Отдельно перечислить невыполненные проверки.
Не писать «полностью готово», если проверен только `/ready` или локальный SDK.
