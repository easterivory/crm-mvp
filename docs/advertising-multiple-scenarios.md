# Несколько рекламных сценариев проекта

## Настройка

В «Рекламном сценарии» сверху выбрать существующий сценарий или ввести название и нажать «Создать сценарий». Новый сценарий выключен и не имеет ботов/слотов.

У каждого сценария отдельные название, боты, защитные теги, тег рекламной аудитории, время перехода и слоты. Например, первый сценарий обслуживает ботов 1 и 2, второй — 3 и 4. В настройках чужое назначение показано возле бота; выбор заблокирован. Проверка также выполняется сервером, включая одновременное сохранение двумя администраторами. Назначение сохраняется и у выключенного сценария.

Старый сценарий становится «Основным». Его слоты, очереди, порядок и история сохраняются. Новые сценарии не получают старую базу автоматически. Предпросмотр и запуск обработки старой базы относятся только к выбранному сценарию и его ботам.

Страница рекламного трекинга, участники и журнал ограничены выбранным сценарием. Статистика доступна и для выключенного сценария. В отдельном рекламном Telegram-боте выбор: проект → сценарий → слот.

## Изменения и ограничения

- Состав очереди фиксируется за сценарием при регистрации участника. Добавление другого сценария не переносит людей и не перезапускает рекламу.
- Бот может быть назначен только одному сценарию, включая выключенные. Для переноса сначала убрать его из прежнего сценария и сохранить настройки. Незавершённые очереди прежнего сценария при следующей обработке останавливаются по прежнему правилу `bot_removed_from_scenario`; автоматического переноса/повторного включения нет. Выключенный сценарий не обрабатывает очереди до включения.
- Для новых рекламных циклов используется текущее назначение бота. Старые завершённые участники не записываются повторно. Правило возврата через явный `/start` после 30 дней без сообщений сохраняется.
- Слоты, добавленные позднее, не дописываются в уже сформированную очередь. Правки ещё не отправленного содержимого подхватываются как раньше.
- Удаления сценариев нет: выключение сохраняет историю и связи очередей.

## Выкатка

1. Сделать и проверить бэкап PostgreSQL и файлов медиа.
2. Остановить старые API и обработчики, которые записывают рекламные данные. Одновременный запуск старого и нового кода не поддерживается: меняется первичный ключ настроек сценария.
3. Применить `alembic upgrade head` до ревизии `20261102_0091`. Миграция транзакционная, с ограничением ожидания блокировок 5 секунд. При ошибке не запускать новый код и не удалять таблицы для обхода ошибки.
4. Запустить согласованные версии API, worker и frontend. Проверить «Основной», его настройки, слоты и участников. Сначала проверить второй сценарий на тестовом боте.
5. Настроить раздельные назначения и только затем включить новые сценарии. Старую базу обрабатывать отдельным подтверждённым прогоном.

Автоматический downgrade запрещён: несколько очередей нельзя безопасно слить в одну. Возврат старого кода после этой миграции требует отдельного плана восстановления; нельзя просто запускать старую версию поверх новой схемы.

## Локальная проверка

Тесты `test_advertising.py` и `test_advertising_scenarios.py` выполняются только на изолированной PostgreSQL через `CRM_TEST_POSTGRES_URL`. Проверяются маршрутизация/отправка по сценариям, конфликты назначений, чужие проекты/слоты/участники/прогоны, миграция настроек и незавершённой доставки, восстановление резервной копии и прежние сценарии отказов доставки. Telegram-отправки подменены: живые лиды в проверках не участвуют.

Результат проверки этой реализации:
- PostgreSQL + рекламные сценарии + проверки скрипта выкатки: 31 passed.
- Общий набор без внешних сервисов: 832 passed, 75 skipped; 7 subtests passed. Это отдельный прогон, числа не нужно складывать как уникальные проверки.
- Сборка frontend и браузерные проверки desktop/mobile прошли; проверено разделение слотов и блокировка ботов, занятых другим сценарием.
- При параллельной тяжёлой сборке общий набор дважды выявил нестабильность старой проверки интервалов транспорта рассылок (порог 45 мс при интервале 50 мс). Отдельно и в финальном общем прогоне без параллельной нагрузки она прошла. Транспорт рассылок этим изменением не переписывался.
- Проверки не заменяют тестовую отправку через настоящего Telegram-бота и проверку миграции на свежей копии production-базы перед выкаткой.
