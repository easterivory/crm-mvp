# Постбэки, протокол 2: проверка и условия запуска

Проверено локально 04.11.2026. Это результат проверки кода, не утверждение о
готовности конфигурации рабочих серверов. Живые постбэки, DNS, секреты и партнёры
не переключались. Основной сервер и отдельный приёмник остаются разными пакетами.

## Что реализовано

- Независимые направления: исходящая подача и входящие события/обратные статусы.
  Гембл не требует исходящей интеграции. Наш домен и полный секретный URL видны
  в настройках; адрес покупателя показан отдельно.
- Точные ID карточки/подачи, scoped Player/Click ID и сохранённый external ID.
  Неоднозначность не разрешается выбором последнего лида. Рекламный tracking_code
  больше не используется как идентификатор человека.
- Два обработчика: REG/FD/RD и настроенные статусы конкретной подачи. Проверка
  денег, времени, ID операции, переходов и конфликтов. Явный общий namespace ID.
- Дедупликация доставки и бизнес-операции, атомарные квитанции и задания.
  Время/ревизия фиксируются при приёме; источник и buyer персональной ссылки
  сохраняются независимо от последующей смены источника чата.
- Версии правил, обычная ротация с перекрытием, аварийный отзыв, архив вместо
  удаления журнала, явный повторный разбор с историей и проверка без записи.
- Durable followups после commit для Sheets/Facebook, существующий DB outbox
  TikTok. Неопределённые внешние отправки требуют сверки, а не слепого повтора.
- Heartbeat, очередь gateway для superadmin, диагностика в интерфейсе и
  operational alerts о потере связи, возрасте очереди, dead и диске.
- Инструкция в CRM: Документация → Постбэки. Подробности: postbacks-setup.md.

Полный регрессионный прогон с одноразовыми PostgreSQL 16 и Redis:
Последний завершённый полный прогон: **975 passed, 5 skipped, 7 subtests passed**,

границ полей/UUID и конкурентности, включая Facebook/TikTok: **86 passed**. Производственные
библиотеки не добавлялись. PostgreSQL/Redis установлены локально только для QA,

## Как повторить профильные тесты

Только одноразовая БД: тесты создают/удаляют случайные схемы и требуют CREATE
SCHEMA. Не подставлять серверную/рабочую базу и Redis CRM.

```sh
DATABASE_URL=postgresql+asyncpg://USER@127.0.0.1:PORT/QA_DATABASE \
CRM_TEST_POSTGRES_URL=postgresql+asyncpg://USER@127.0.0.1:PORT/QA_DATABASE \
CRM_TEST_REDIS_URL=redis://127.0.0.1:REDIS_PORT/0 \
REDIS_URL=redis://127.0.0.1:REDIS_PORT/0 \
.venv/bin/python -m pytest -q tests/test_postback_contracts.py tests/test_postback_relay.py tests/test_postback_gateway.py tests/test_postback_gateway_process.py
```

Полный регрессионный прогон с теми же переменными: убрать список файлов тестов.
Проверки UI: frontend/tests/run-postbacks.mjs; нужен локальный Vite и Playwright.

## Не проверено здесь: условия перевода живого трафика

1. Docker image build/start, VPN, TLS/firewall двух хостов и согласованный
   callback на отдельной тестовой карточке. Docker engine локально недоступен;
   процесс uvicorn проверен, но это не замена тесту контейнера/volume на хосте.
2. Миграция на актуальной копии рабочей базы с замером длительности/блокировок.
   Тест сохранности на синтетических старых данных не заменяет эту проверку.
   Нужны свежий бэкап, окно низкой нагрузки и проверка API/jobs после миграции.
3. Актуальный контракт каждого партнёра: ID, время, названия статусов, ACK,
   повторы 429/503. Старые синтетические примеры не подтверждают конкретного
   партнёра. Специфические подписи/raw multipart этого пакета не поддерживаются:
   вход защищён секретным URL, транспорт подписан HMAC. Старый прямой /pb
   сохраняет поддержку текстовых multipart-полей, но gateway их не принимает.
4. Нагрузочный профиль из исходного ТЗ: 1/сек 10 минут, 20/сек минуту вместе
   со стартами/ответами/чтением чатов на сопоставимом стенде. Здесь не измерены
   p95/p99, серверный потолок или влияние на новые старты. Последовательный
   gateway по умолчанию <5 доставок/сек с учётом HTTP, не обещать ему 20/сек
   непрерывного дренирования. Пики должны покрываться ёмкостью/сроком очереди.
5. Сверка старых callback URL. До переноса старые неаутентифицированные
   partner-status routes намеренно остаются открытыми ради совместимости.
   Новые интеграции закрыты по умолчанию. Закрыть старые поштучно в CRM или
   глобально LEGACY_PARTNER_POSTBACKS_ENABLED=false ПОСЛЕ согласования.
6. Внешний мониторинг приёмника независимо от CRM; бэкапы SQLite вне хоста,
   восстановление контейнерного volume и согласованная точка восстановления
   PostgreSQL/SQLite. Не удалять ledger/очередь и не запускать down -v.

Ни одна миграция не пересчитывает старую статистику и не назначает VIP/теги.
Историческая атрибуция без сохранённого личного ID не восстанавливается догадкой.
Existing lifecycle reports сохраняют UTC-границы; отдельного перевода на МСК нет.
Exactly-once внешнего append без idempotency key партнёра не обещается.
