# Выкладка исправлений доставки от 6 ноября

Только основной сервер CRM. Gateway, SSH, firewall, DNS, Telegram endpoints и секреты
это обновление автоматически не меняет. Новые библиотеки не требуются.

## Что меняется

- Рассылки: новая форма с удержанием кнопки теперь передаёт серверное подтверждение
  большой аудитории и при немедленной отправке, и при планировании. Серверная защита
  аудитории больше 1000 не отключается. Незавершённое удержание отменяется при уходе
  со шага; параллельные вызовы запуска из формы блокируются. Ошибки валидации API
  показываются с причиной. При сетевом/5xx сбое предлагается сначала обновить список,
  а не автоматически повторить потенциально уже сохранённый запуск.
- Сохранение полей проверяет ограничения БД до UPDATE. Для текстового вопроса,
  сохраняющего страну, длинный ответ/ссылка вызывают существующий fallback, а не
  бесконечное падение. Исходное сообщение остаётся в переписке.
  Ошибка хранения не расходует обычный счётчик отказов и не ведёт дальше даже при
  нуле повторных попыток: шаг ждёт корректный ответ. CRM-действия и
  legacy mappings также не могут записать слишком длинную строку: ошибка явно
  фиксируется, данные молча не обрезаются.
  Если старый блок намеренно сохранял произвольный текст/ссылку в country, ему нужен
  подходящий custom field, а не поле страны. Автоматически такие блоки не переписываются.
  Числа также проверяются по диапазону типа БД: 16-значный ответ вместо возраста
  вызывает fallback на том же шаге. Бизнес-пороги возраста/ветки отказа не меняются.
- Повторяются только известные временные SQL-ошибки до commit/внешней отправки.
  Не более RUNTIME_DISPATCH_MAX_FAILURES (по умолчанию 5) с backoff 5/10/20/40 секунд.
  Постоянная ошибка данных сразу review. Счётчик ошибок отделён от attempts постановки
  в Redis; ожидание ответа/таймера и потеря enqueue ACK не расходуют лимит ошибок.
- Новая диагностика сохраняет SQLSTATE, класс/поле/код ошибки, количество отказов и
  признаки commit/внешней отправки; без исходного ответа клиента/SQL-параметров.
  SQLAlchemy скрывает параметры в исключениях. Медленные API-запросы (от 1 секунды)
  логируются по шаблону маршрута, без query/body; X-Request-ID связывает ответ с логом.
- Настройки → Задания воронок: просмотр review/pending/running выбранного проекта,
  ссылка в чат. Повтор доступен только администратору, по одному заданию, с основанием,
  аудитом и проверкой неизменности чата/последнего ответа/состояния воронки.
- Старые review без новой доказательной диагностики НЕ становятся доступными для
  автоматического повтора. 28 заданий из архива нужно сверять отдельно на сервере;
  этот патч их не запускает и не считает доставленными.
- Рекламные слоты: durable claim, повторная проверка защиты после claim, сеть без
  удержания Chat FOR UPDATE или транзакции. Результат и история каждого сообщения
  сохраняются вместе. ConnectError/ConnectTimeout/PoolTimeout до передачи и 429
  допускают ограниченный повтор (ADVERTISING_DELIVERY_MAX_ATTEMPTS, по умолчанию 3).
  Read/WriteTimeout, 5xx и неизвестный результат не повторяются вслепую.
- Уже подтверждённые сообщения не повторяются при сбое следующего. Старые sending
  без журнала прогресса остаются uncertain. Новая незавершённая отправка считается
  живой в течение ADVERTISING_DELIVERY_STALE_SECONDS (по умолчанию 300).
  Старые uncertain/failed/sent патч не переписывает. Защитный тег или остановка после
  начала сетевого запроса не могут отозвать уже начатую отправку, но блокируют следующую.
- Глобальные настройки → Резервные копии: диагностический статус пишет именно
  backup-worker при старте и выполнении задачи. Видны host, эффективный лимит,
  размер/локальная готовность/подтверждение Telegram. Адрес с паролем/секретами не выдаётся.
  Облачный API не позволяет обойти лимит простой заменой числа в переменной.

## Порядок выкладки

1. Свежий бэкап и проверка восстановления на отдельной БД. На полной копии применить
   миграции до 0097, проверить старые чаты/лиды/сообщения и состояния очередей.
   Здесь тестируется изолированная БД с контрольными данными, не полный production dump.
2. Добавочная миграция `20261106_0097` идёт после `0096` (офферы). Добавляет failure_count
   и diagnostics_json в runtime_dispatches, progress_json в advertising_deliveries.
   Старые записи получают 0/пустой JSON, а не выдуманные доказательства отсутствия отправки.
   Downgrade с уничтожением прогресса запрещён; lock_timeout 5 секунд. История не удаляется.
3. Остановить пишущие API/worker/jobs на короткое окно, применить миграции, обновить
   и запустить вместе API, worker и jobs. Обновить backup-worker и frontend/dist.
   Собрать frontend через npm run build: по умолчанию сервер монтирует dist, а не
   исходники TSX. Не ограничиваться пересборкой Python Docker-образа.
   Не оставлять старый worker рядом с новым на одной очереди: он не понимает progress_json.
   Не запускать dev deploy/seed/reset на production и не удалять volumes/очереди.
4. Проверить новый тестовый чат: нормальный ответ; длинная страна/рекламная ссылка;
   следующий корректный ответ; сохранность истории и отсутствие повтора одной ошибки.
5. Настройки → Задания воронок: сверить review. У старых записей отсутствие кнопки
   повтора намеренно. Нельзя делать UPDATE status=pending всей очереди.
6. Для диагностических проверок выполнить:

   ```sh
   bash scripts/check-crm-delivery.sh -f docker-compose.yml
   ```

   Если используются override/project-name, передать ТОТ ЖЕ набор аргументов.
   Скрипт ничего не перезапускает и не изменяет. Использовать после миграции 0097.

## Большой бэкап: необходимая настройка сервера

Это не включается автоматически. Согласовать отдельный Local Bot API только для backup-бота.
Сохранить действующие идентификаторы compose-проекта и volumes.

1. В .env основного сервера задать отдельные BACKUP_LOCAL_API_ID/BACKUP_LOCAL_API_HASH.
   Не использовать/не переносить Telegram user sessions или клиентские bot tokens.
2. Использовать существующий opt-in `docker-compose.backup-local-api.yml` вместе с
   основным compose. При необходимости переноса backup-бота с cloud выполнить ранее
   согласованный порядок logOut/подключения Local API, не переключать бот вслепую.
3. Пересоздать backup, а также службы, использующие того же backup-бота для алертов,
   с теми же override. Профиль задаёт BACKUP_TELEGRAM_API_BASE_URL и лимит 2000 МБ.
   Не открывать порт Local Bot API наружу и не разворачивать postback gateway на main.
4. Проверить effective configuration именно в backup-контейнере через скрипт выше.
   Наличие файла override в репозитории не означает, что он применён к контейнеру.
5. Выполнить согласованную отправку архива больше 49 МБ, проверить файл в Telegram,
   контрольную сумму и восстановление на отдельной БД. До этого большая внешняя
   копия не считается проверенной. Простой тест getMe недостаточен.
6. В следующих выкладках сохранять тот же compose profile; не запускать plain compose
   с другим набором файлов/именем проекта. Никакой автоматической очистки старых копий
   или volumes ради включения Local API.

## DNS и SSH

Проверить resolver из worker и хоста, время сбоев и сетевые ошибки Docker. Не менять
DNS всех контейнеров без проверки используемой VPN/локальной сети.
Для SSH сначала проверить рабочий ключ и независимую резервную сессию/консоль,
проверить sshd -t; только затем отдельным согласованным изменением ограничивать
парольный доступ. Этот патч не закрывает SSH и не меняет правила firewall.
