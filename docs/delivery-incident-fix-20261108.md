# Исправление остановок и конкуренции за БД, 08.11.2026

Только основной сервер CRM. Выполнена локальная реализация и изолированные проверки.
Это НЕ разрешение на выкладку, replay, изменение Telegram, gateway или секретов.

## Основание

17 новых/затронутых runtime review в «Вакансиях». По времени, боту и контексту

сработал таймаут durable intake 5 секунд. Рядом есть успешный workspace-counts
длительностью около 50 секунд. Это не доказательство падения PostgreSQL/Redis
или отказа Telegram API в приёме именно этого webhook.

## Воронки и доставка

- В активном runtime сохраняется TelegramDeliveryError, а не общий HTTPException.
  Коды, метод, признаки блокировки/деактивации и определённости доступны в диагностике.
- Для Bot API при ConnectError/ConnectTimeout/PoolTimeout до отправки либо явном
  429, при наличии точной контрольной позиции, создаётся новое durable-задание
  существующего scheduled worker. Повторяется конкретный индекс сообщения либо
  начальная отправка вопроса. Это НЕ повтор старта, ответа или CRM-действия.
- Привязка: chat, ID состояния, step, entered_step_at. Перед постановкой и выполнением
  проверяются тот же заход, отсутствие паузы/завершения/сброса, активные проект/бот.
  Старые активные прохождения остаются на прежней опубликованной версии.
- Сохраняются индекс, ответ для дальнейшего ветвления, completion edge и факт
  завершённого typing. Уже принятые сообщения и предыдущие действия не отправляются
  и не выполняются второй раз. Задержка/typing перед этой попыткой не запускаются заново.
- Original dispatch помечается done одновременно с созданием continuation и его
  outbox dispatch. Это означает «обработка передана продолжению», не «сообщение уже
  доставлено». Связь хранится в diagnostics.continuation_job_id/delivery_outcome;
  safe_to_replay исходной обработки остаётся false. Исторический отказ сохраняется
  в диагностике, а last_error у завершённого исходного dispatch очищается.
- Используются существующие backoff/max-attempts scheduled worker; бесконечного
  цикла нет. Новый длительный сбой заканчивается failed/alert, а не повтором всего пути.
- Read/WriteTimeout, неоднозначные 5xx и отсутствие доказательной позиции не дают
  права на автоматический повтор. Исходная обработка остаётся review; в scheduled
  worker неизвестная доставка завершается failed с delivery_uncertain=true.
- Прерванное running-продолжение после перезапуска worker не возвращается автоматически
  в pending: результат мог быть принят Telegram. Нужна отдельная ручная сверка.
  Для прежних заданий без нового visit-маркера старое stale-восстановление не меняется.
- Блокировка и деактивация — отдельные конечные исходы. Автоматизация приостанавливается,
  история не удаляется; деактивация не выдаётся за пользовательскую блокировку.
  Более новое событие разблокировки не перезаписывается старым отказом отправки.
- Автопродолжение не распространено на MTProto: там один элемент иногда содержит
  несколько RPC (например, кружок и текст вариантов), и отказ последнего RPC не
  доказывает отсутствие первой отправки. Такие ситуации не повторяются вслепую.
- Доставка служебных повторных напоминаний/других операций без точной позиции также
  не превращается в общий replay. Никаких массовых «оживлений» старой базы нет.

## Пулы и счётчики

- Общий pool API/worker не увеличивается и не перенастраивается.
- В API лениво выделяются два независимых bounded pool: intake — 2 соединения,
  counters — 1, без overflow. Считать бюджет **+3 подключения на процесс API**,
  умножая на число процессов/реплик. Workers эти пулы не создают.
- Приём Telegram не зависит от Redis и не ждёт свободного подключения общего
  пула, занятого UI. Возвращается 200 только после commit inbox, иначе 503 для
  повторной доставки Telegram. Проверка бота читает только его ID, не весь ORM/токен.
- У reserved pools connect timeout 2s, pool wait 0.5s, statement timeout 3s,
  lock timeout 1s; у counter operation отдельный deadline 4s, у intake
  сохранён внешний deadline 5s. Таймауты не протекают в прежний общий pool.
- Pool счётчиков серверно read-only. Тяжёлый расчёт не может занять общий pool
  либо соединения приёма обновлений. Истечение таймаута не возвращает выдуманный ноль.
- Один агрегат по проекту/выбранным ботам обслуживает разных менеджеров. В SQL
  переиспользуется уже присоединённая карточка вместо повторных коррелированных
  поисков Lead. «Мои» и доступное «Все» вычисляются отдельно по текущему пользователю.
- Redis cache — 3 секунды, отдельный namespace. Ключ включает проект, его ревизию,
  настройки и нормализованные bot filters. Карта назначений остаётся внутренней;
  клиенту не возвращаются чужие персональные счётчики или IDs менеджеров.
- NX-lock объединяет параллельные одинаковые расчёты. На ожидании кэша общий SQL
  connection уже освобождён. При отказе Redis остаётся ограничение одним counter
  connection; бесконечного ожидания/неограниченного числа сканов нет.
- В счётчиках освобождение просроченных назначений выполняется пакетами до 100 с
  прежним аудитом и бюджетом 2s. Остаток не удаляется; следующие запросы/штатные
  операции продолжают обработку. Остальные вызовы lease service сохраняют прежние
  параметры и поведение. Бизнес-правила продления/истечения не меняются.
- Числа вкладок могут отставать до 3 секунд. Список сообщений/чатов, read/unanswered,
  теги, источники, дневная статистика, подсчёт первых стартов/лидов не кэшируются
  этим механизмом и не пересчитываются по новой методике.

## Проверки

Итог финального общего прогона с CRM_LARGE_QA=1: **1183 passed, 5 skipped,
7 subtests passed**, 158.03s. Все 23 сценария/варианта нового incident-файла,
включая 100k workload, прошли. Compileall и git diff --check без ошибок.
Существующие предупреждения multipart/crypt и FK-циклов тестовых fixtures
остались; пропущенные тесты не объявляются прошедшими. Production не вызывался.

Основной файл: `tests/test_incident_20261108.py`. Проверяются на настоящем локальном
PostgreSQL: частичная отправка двух сообщений, начальный вопрос, однократное действие,
неповторяемость исходного dispatch; сетевой неопределённый результат, смена visit,
пауза/reset/архив/MTProto; блокировка/деактивация/новая разблокировка; совместимость
Chat lock с FK-вставкой сообщения; interruption/restart fence и пределы retry.

Для счётчиков: 20 параллельных запросов разных менеджеров -> один SQL aggregate,
точные персональные результаты, expiry cache, эквивалентность приоритетного фильтра.
Для intake: заняты общий pool и pool счётчиков, 20 webhook durably принимаются
через отдельный pool; ни Redis, ни исполнение воронки для ACK не нужны.

Отдельный workload на 100 000 синтетических чатов (+3 fixture-карточки):
прежний per-viewer aggregate **307.6 ms**, новый shared aggregate **206.5 ms**,
все метрики совпали. Это локальный замер, не обещание production p95. Состав
синтетики не заменяет полную копию базы/реальные распределения активности и SQL.
Запуск: с локальными CRM_TEST_POSTGRES_URL/DATABASE_URL/Redis и CRM_LARGE_QA=1,
`python -m pytest -q -s tests/test_incident_20261108.py::test_counts_on_one_hundred_thousand_synthetic_chats`.
Без явного флага тяжёлый workload пропущен, а обычные регрессии запускаются.

## Выкладка отдельным диалогом после согласования

1. Уточнить фактическую ревизию/миграцию, состав compose overrides и project name.
   Проверить свежую восстанавливаемую внешнюю копию и запас PostgreSQL max_connections:
   +3 на API process, плюс прежние сервисы и административный резерв.
2. У самого incident fix нет новой DDL/миграции и массового UPDATE истории. Но текущая
   ветка также содержит opt-in cloud assistant 0098: при выкладке ВСЕЙ ветки сначала
   проверить/apply 0098 на копии согласно cloud-assistant-setup.md. Не запускать новый
   ORM без соответствующих колонок даже при выключенном помощнике.
3. Обновлять API/worker/jobs согласованно. Не оставлять старый jobs worker на новых
   continuation payload: он не знает visit/restart-fence. Не применять dev seed/reset,
   не удалять volumes, очереди, runtime state или журнал dispatch.
4. Не выполнять UPDATE review->pending или restart воронок всем 17/73 случаям.
   Старые доставки требуют сверки истории/Telegram по конкретному чату отдельно.
5. Проверить /health, новые durable inbox, прогресс новых start/input, ошибку отправки
   с последующим continuation, отсутствие дублирования и counters разных менеджеров
   на согласованном QA-боте. Не создавать тестовые конверсии/депозиты реальным лидам.
6. Сравнить API latency, число SQL connections/ожиданий, counter 503, intake 503,
   scheduled failures и review. Не увеличивать общий pool/таймауты вслепую.
7. При необходимости отката сначала согласовать судьбу новых pending/running
   continuation. Старый worker не должен автоматически подхватить их без новых
   проверок. Предпочтительнее исправление вперёд; таблицы/историю не удалять.

## Что этот патч не объявляет исправленным

- Причину сетевого ConnectError до Telegram нельзя определить/устранить локальным
  изменением бизнес-кода. Нужны отдельные сетевые замеры сервера; VPN/kernel warnings
  сами по себе не доказывают причинную связь.
- 82 analysis_unresolved: fallback не равны 82 инфраструктурным остановкам. В доступных
  файловых логах найдено 67 применений route=fallback/source=ai/error_code=None;
  код переводит на настроенный fallback. Смысл ответов/настройки ИИ и исторические
  runtime logs этим патчем не переписываются.
- 39 scheduled done с историческим last_error не считаются недоставленными.
  Advertising cancelled не превращаются в failed и не возобновляются.
- Большой backup 737.2 MB не отправится через cloud API с лимитом 49 MB от этих
  правок. Нужна отдельно согласованная настройка существующего backup-local-api
  либо внешнего хранилища. Порядок: delivery-incident-fix-20261106.md. В рамках
  этой задачи профиль/бот не переключались, локальный production-файл не проверялся.
