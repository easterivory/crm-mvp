# MAIN CRM: исправление зависания 04.11.2026

Этот документ относится только к основному серверу CRM. Отдельный postback
gateway не обновлять и не разворачивать на основном сервере для этого фикса.

## Что подтвердили серверные логи

- Redis 13:28–13:33 UTC: задержки AOF fsync; PostgreSQL в том же окне:
  checkpoint sync до 25 секунд, отдельная синхронизация почти 19 секунд.
- SAR: CPU steal 22%, load1 26.16 при 4 CPU, очередь выполнения 63,
  заметное давление I/O. Это общая деградация хоста, не только ошибка CRM.
- Docker не успевал запускать healthcheck, были таймауты DNS.
- PostgreSQL показал конфликт `SELECT chats ... FOR UPDATE` с `UPDATE chats`.
  Проверка на реальной PostgreSQL воспроизводит опасное повышение FK KEY SHARE
  блокировки при вставке сообщения. Runtime теперь использует NO KEY UPDATE:
  писатели чата по-прежнему сериализованы, FK-вставки не создают этот цикл.
- В API было 360 исчерпаний пула соединений; в worker — 870 ошибок пушей,
  среди них повторные попытки писать деактивированным аккаунтам.
- Задача 6bcea57b фактически завершилась за ~19 секунд. Старый текст про
  300 секунд подставлялся к любому пустому TimeoutError и вводил в заблуждение.

Фикс уменьшает усиление внешнего сбоя приложением. Он не исправляет CPU steal,
медленный диск, DNS и проблемы виртуализации. Проверить это отдельно у хостера;
не отключать AOF/fsync ради скорости и не увеличивать вслепую число подключений.

## Новая обработка

1. Webhook проверяет секрет/формат и сохраняет исходное обновление в
   `telegram_inbox`. Уникальность — `(bot_id, update_id)`. HTTP 200 только после
   commit; если сохранить не удалось — 503. Redis и воронки в запросе не вызываются.
2. DB worker разбирает сохранённые события, ограниченно параллельно, сохраняя
   порядок уже принятых событий одного диалога. Чат, сообщение и задание start/input
   сохраняются вместе. Нет inline-запуска воронки при недоступном Redis.
3. Задания start/input, подсказки для отложенных задач и typing сохраняются в
   `runtime_dispatches` внутри исходной транзакции. Передача Redis происходит
   после её завершения, без соединения БД и блокировки чата.
4. Input/start ожидают подтверждения обработчиком. Перед исполнением отдельно
   фиксируется `running`: остановка процесса не может незаметно разрешить повтор.
   Потеря ответа
   Redis приводит к повторной постановке с прежним ARQ ID, не с новым случайным ID.
   Намеренное ожидание следующего шага переносит срок dispatch, а не теряет ответ.
   Для этих двух функций ARQ не хранит финальные результаты: источником истины
   служит БД. Поэтому временный отказ до внешних эффектов не блокируется часовой
   записью failed в Redis. Существующие имена/аргументы заданий сохранены.
   Старое восстановление пропущенных стартов не перехватывает новые задания и
   не помечает повторный /start обработанным до его очереди. Частичный захват
   пачки входящих откатывается целиком; необработанный ответ остаётся для повтора.
5. После частичного commit/возможной внешней отправки ошибка переводит новое
   задание в `review`: автоматический повтор запрещён, нужен разбор. Прерванный
   обработчик входящего/исполнения также переходит в review после истечения времени.
   Это защита от дублей, НЕ обещание exactly-once для Telegram: у Bot API нет
   общего ключа идемпотентности для отправки сообщения.
   Следующая пачка ответов не включает сообщения, уже требующие review.
6. При deactivated-user пуши приостанавливаются, не помечаются отправленными.
   Существующая логика возобновления по новому входящему/входу на шаг сохраняется.
7. Таймауты отложенных задач содержат реальный этап, лимит и длительность.

Старые failed задачи не перезапускаются массово. Старые правила воронок, теги,
карточки, история, паузы менеджера и таймеры не пересчитываются и не сбрасываются.
Дедупликация сообщений и проверка текущего состояния воронки сохранены.

## Выкладка

1. Сделать и проверить бэкап PostgreSQL; сохранить текущую ревизию и образы.
   Не удалять volumes. Не использовать dev-seed как часть ручной prod-выкладки.
2. Собрать новый MAIN-образ. В согласованное окно приостановить приём штатной
   maintenance-схемой (не отвечать ложным 200 на несохранённые webhooks), дождаться
   окончания активных отправок jobs, затем остановить писателей. Не убивать
   принудительно выполняющуюся отправку: если дренирование невозможно, записать
   активные задачи для сверки, а не автоматически повторять их после выкладки.
   Проверить текущую миграцию; для существующей базы после 0094 нужен
   `alembic upgrade head` до **20261105_0095**. Если миграция падает, не запускать
   новый API, не делать stamp и не править старые таблицы вручную.
3. Запустить согласованные версии `worker`, `jobs`, `api` и `mtproto`.
   Режим `python -m app.workers`/`all` уже включает новый DB worker.
   При собственной раскладке отдельных процессов обязательно запустить
   `python -m app.workers telegram-delivery` в одном выделенном процессе.
   Не поднимать его одновременно отдельно и в all без необходимости.
4. Проверить heartbeat `Telegram delivery heartbeat`, возраст pending и review,
   очередь jobs, обычные ответы и один старт на отдельном тестовом боте.
   Проверки с реальной отправкой — только после явного согласования владельца.
5. Не восстанавливать автоматически задания из аварийного окна: сначала сверить
   отправленные сообщения, состояние шага и последующие ответы менеджера.

0095 создаёт только две новые таблицы и индексы на них, не меняет старые строки.
Downgrade с удалением очередей запрещён: там могут быть уже подтверждённые входящие.
При откате нельзя оставлять принятые pending события без совместимого обработчика.
Для уже принятой очереди сохранять новый delivery worker/jobs либо отдельно
согласовывать её остановку/разбор; простой возврат всех старых образов недостаточен.

Проверка 0095 выполняется отдельно на PostgreSQL со схемой перед этой миграцией.
Полная историческая установка с пустой базы сейчас имеет старую проблему 0012:
повторное добавление `waiting_for_answer` после baseline. Этот фикс её не меняет;
это не повод применять stamp к существующей рабочей базе.

## Настройки и наблюдение

```dotenv
TELEGRAM_INBOX_CONCURRENCY=4
TELEGRAM_INBOX_TIMEOUT_SECONDS=120
TELEGRAM_INBOX_MAX_ATTEMPTS=5
TELEGRAM_INBOX_RETENTION_DAYS=30
RUNTIME_REDIS_TIMEOUT_SECONDS=2
RUNTIME_REDIS_MAX_CONNECTIONS=10
```

Успешные транспортные квитанции чистятся небольшими порциями спустя 30 дней.
Pending/review не удаляются автоматически; история чатов не затрагивается.
Таблицы автоматически входят в обычный PostgreSQL-бэкап. Payload входящих содержит
персональные данные: доступ только доверенным администраторам, не публиковать дамп.

Безопасные запросы наблюдения (без текстов сообщений/секретов):

```sql
SELECT status, count(*), min(created_at) FROM telegram_inbox GROUP BY status;
SELECT kind, status, count(*), min(created_at)
FROM runtime_dispatches GROUP BY kind, status;
SELECT id, bot_id, update_id, attempts, last_error
FROM telegram_inbox WHERE status = 'review' ORDER BY created_at LIMIT 100;
SELECT id, dedupe_key, kind, attempts, last_error
FROM runtime_dispatches WHERE status = 'review' ORDER BY created_at LIMIT 100;
```

Не менять review на pending пачкой: сначала проверить внешние эффекты и текущую
воронку. Алерты `telegram_inbox`, `runtime_dispatch`, `telegram_delivery` используют
штатный cooldown; метрики доступны в heartbeat даже при подавлении повторного алерта.

боевых токенов и Telegram-сессий тесты не используют.

  недоступной очереди. Это локальная проверка обработки входящих, не тест
  пропускной способности production с Telegram/ИИ/медиа и не гарантия мощности VPS.

  проблема исторического пустого baseline описана выше и в этот фикс не входит.
