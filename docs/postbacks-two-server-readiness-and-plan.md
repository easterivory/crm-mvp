# Постбэки между двумя серверами: аудит и ТЗ

> Исторический аудит до изменений от 03.11.2026. Текущее поведение описано в
> [инструкции](postbacks-setup.md), результаты и оставшиеся условия запуска — в
> [проверках протокола 2](postbacks-v2-verification.md). Замечания ниже не являются
> утверждением, что соответствующая ошибка сохранилась после реализации.

Дата: 03.11.2026. Основание: текущий код репозитория, документация развёртывания,
профильные локальные тесты. Конфигурация и доступность рабочих серверов НЕ
проверялись. Это план следующих изменений, а не отчёт об их реализации.

## 1. Заключение

Подготовлен отдельный транспорт для входящих событий лида: внешний HTTPS →
дисковая очередь gateway → подписанный запрос в CRM → транзакция PostgreSQL.
Это пригодная основа для стенда, но не законченная интеграция для всех проектов.

Для гембла есть события registration/deposit/redeposit и их подсчёт в трекинге.
Для подачи есть отдельный старый обработчик статуса заявки, который новый relay
НЕ вызывает. Передавать обе категории в общий прод сейчас не рекомендовано.
Обещание «без багов» невозможно; допуск к запуску должен опираться на измеримые
проверки ниже, а не на общее количество зелёных тестов CRM.

## 2. Что уже реализовано

| Область | Текущее состояние |
|---|---|
| Изоляция | Отдельная папка, Dockerfile, compose, nginx; исключена из основного Docker build |
| Приём | GET, POST JSON object, URL-encoded form; ограничения размеров; секрет в URL |
| Сохранность | SQLite WAL + synchronous FULL, подтверждение после записи, постоянный volume |
| Передача | HMAC по методу/пути/времени/телу, окно 60 сек, фиксированный адрес CRM, без redirects |
| Права | Явный список проектов в CRM; manifest содержит хеши активных endpoint-секретов |
| Повторы транспорта | Неизменные UUID и тело; ledger в PostgreSQL в одной транзакции с событием |
| Ошибки | Сетевые/5xx/429 повторяются; терминальные ошибки остаются в dead; ручной retry с прежним ID |
| Настройка | Панель PostbackEndpointsPanel внутри настроек партнёров: тип, поля, идентификатор, сумма, валюта, event ID |
| Диагностика | Квитанции доставленных событий в CRM; очередь/ошибки gateway доступны через локальную CLI |
| Совместимость | Relay выключен по умолчанию, старый /pb остаётся включён; новый домен не меняет BASE_URL CRM |

Инфраструктура задаётся переменными окружения, НЕ через CRM:
основной сервер — POSTBACK_RELAY_ENABLED, POSTBACK_RELAY_SECRET,
POSTBACK_RELAY_PROJECT_IDS, POSTBACK_PUBLIC_BASE_URL, POSTBACK_DIRECT_ENABLED;
gateway — CRM_ORIGIN, RELAY_SECRET и лимиты очереди. WireGuard, firewall, DNS и
TLS описаны в инструкциях, но не были настроены автоматически.

Исходящая подача CRM → покупатель остаётся на основном сервере. Внешний приёмник
не скрывает его исходящий IP от покупателя и не переносит исходящие запросы.
Если требуется и скрытие исходящего IP, это отдельное согласованное требование
к ограниченному исходящему прокси, а не доступ gateway ко всему API CRM.

## 3. Подтверждённые пробелы

### P1. Обратные статусы подачи не проходят через relay

`app/api/v1/routers/partners.py:53` публикует
`POST /api/v1/partners/postbacks/{integration_id}`. Он вызывает
`PostbackService.process_partner_postback`, меняет partner_status, статус лида,
валидность подачи и запускает связанные триггеры.

Relay вызывает только `PostbackEndpointService.receive`, который создаёт
LeadEvent. Событие с именем accepted/qualified само по себе НЕ обновляет подачу.
Также нынешний POSTBACK_DIRECT_ENABLED не закрывает старый маршрут partners.

### P1. У старого маршрута статусов нет аутентификации в приложении

В маршруте и вызываемом обработчике нет проверки секрета, HMAC или авторизации
отправителя. При публичной доступности и известных ID возможна подмена статуса.
Фактические серверные ограничения доступа не проверялись. Не закрывать этот
маршрут вслепую: сначала инвентаризация действующих отправителей и миграция.

### P1. Неоднозначное сопоставление лидов

`app/services/postback_endpoint_service.py:308` и далее:
- telegram_id выбирает последнюю карточку среди ботов проекта;
- tracking_code выбирает последнего лида источника, а не конкретного человека;
- click_id допускает поиск подстроки во всём JSON;
- external_id ищется подстрокой в request/response JSON подачи.

Старый поиск подачи в `app/repositories/partner_repository.py:322` также содержит
подстрочный fallback. Это риск присвоить конверсию другому лиду. Транспортная
подпись такую ошибку не исправляет. Для безопасного ограниченного стенда сейчас
годятся точные lead_id/chat_id, но это не закрывает остальные замечания.

### P1. Дедупликация бизнеса слабее дедупликации транспорта

Новый запрос партнёра получает новый delivery_id. Защита LeadEvent работает
только при наличии external_event_id и только в рамках endpoint.
Повтор одного ID с другим лидом/типом/суммой возвращает старое событие без
проверки конфликта. ID обрезается до 255 символов. Без ID повторный редепозит
может учитываться повторно; другой endpoint может создать ещё одно событие.
Разные реальные платежи с одинаковой суммой нельзя объединять по телу запроса.

### P1. Время и источник могут относиться к моменту доставки, не события

В mapping нет поля времени. receive не передаёт occurred_at; record_event
ставит текущее время CRM и берёт текущие tracking_link/funnel из чата.
Очередь, восстановленная на следующий день, способна изменить день статистики.
Если источник карточки менялся, поздний постбэк может получить новый источник.
Время приёма gateway в envelope тоже отсутствует.

### P1. Денежные значения недостаточно валидируются

_parse_amount принимает Infinity, величины за пределами Numeric(18,2) и лишнюю
точность. Это воспроизведено локально вызовом функции без записи в БД.
Ошибку данных нельзя превращать в бесконечно повторяемую ошибку сервера.

### P2. Изменение настроек и восстановление недоставленных событий

Mapping читается в момент обработки: редактирование endpoint может иначе
интерпретировать уже принятую очередь. Ротация секрета оставляет старые ещё не
обработанные события с 404/dead. unmatched подтверждается как доставленное и
автоматически повторно не разбирается. Удаление endpoint каскадно удаляет его
квитанции; это неподходящее поведение для постоянного журнала разбирательств.

### P2. Эксплуатация и производительность не подтверждены

Manifest устаревает через 300 сек: gateway прекращает новый приём при долгой
недоступности CRM. Это нынешняя политика отзыва секретов, а не бесконечная
автономная работа. Передача последовательная с паузой 0.2 сек: верхняя граница
ниже 5 событий/сек с учётом HTTP. Один таймаут задерживает другие проекты.
В nginx пример 5 запросов/сек на IP, 50 суммарно; партнёр может слать всё с одного
адреса. Фактическая пропускная способность не измерена.

В CRM нет состояния связи/возраста очереди/автоалертов gateway. /ready проверяет
приём, но не доказывает успешную бизнес-обработку. Тело ответа accepted может
не совпасть с ожидаемым ACK конкретного партнёра. Multipart не поддерживается.

Регистрация и первый депозит в lifecycle-отчёте считаются первым событием на
карточку, редепозиты повторяемы. Не менять это попутно на уникальных людей.
Фильтрация дат lifecycle сейчас использует UTC; границы отчётов/МСК проверить
и согласовать, не менять исторические цифры скрытой миграцией.

## 4. Целевая реализация

### Этап A. Контракты и безопасное сопоставление

1. Собрать примеры фактических callback каждого партнёра: метод, Content-Type,
   raw body/query, подпись, ID события, ID пользователя/заявки, время, валюта,
   статусы, правила повторов и ожидаемый ACK. Секреты и ПДн в фикстурах заменить.
2. Один endpoint принадлежит проекту и партнёру; тип обработки выбирается явно:
   lifecycle_event (регистрация/депозит/редепозит) или submission_status.
   Тип проекта задаёт предлагаемые настройки, но не заменяет контракт партнёра.
3. Точное сопоставление: lead_id/chat_id; для подачи submission_id и сохранённый
   partner external ID; для гембла персональный click/sub ID или partner player ID.
   Нужна индексированная таблица соответствий с project/integration/entity scope.
   Источник рекламной ссылки НЕ является идентификатором лида.
4. При исходящей подаче сохранять точный внешний ID ответа, а не искать его
   подстрокой JSON. Обеспечить передачу/возврат нашего correlation ID.
   Для гембл-ссылки проверить полный путь: персональная ссылка в сообщении/кнопке
   → переход → sub ID у партнёра → callback. Не считать настройку поля в UI
   доказательством, что этот ID фактически передаётся.
5. Ноль совпадений → unmatched; больше одного → ambiguous. Никакого «последнего».
   Telegram ID допускается только с достаточным bot/partner scope либо при
   единственном совпадении. Старые unsafe mappings показывать как требующие
   перенастройки; не переводить их на новую семантику без отчёта и согласования.

### Этап B. Единый приём и две бизнес-ветки

1. Общая аутентификация, валидация, журнал приёма и доставка для обеих веток.
   Gateway не получает базу лидов, токены Telegram или право менять произвольные
   сущности. Тип обработки выбирает серверная конфигурация, не входной payload.
2. submission_status должен применяться к конкретной подаче: partner_status,
   is_valid, статус лида и явно настроенные действия. Не ставить VIP/теги без
   настроенного правила; сохранить действующий подсчёт целевых лидов по тегам
   или статусам и существующие правила уникальных стартов.
3. Ввести дедупликацию статусов и защиту от старых уведомлений: хранить версию
   или время события партнёра и таблицу допустимых переходов. Исправления и
   отмены разрешать отдельными явно оговорёнными событиями, не общим «не понижать».
4. lifecycle_event: ограниченный словарь/таблица алиасов, обязательные поля
   по типу, Decimal.is_finite(), границы и согласованная точность денег/валюты.
   Неизвестные типы/статусы сохранять как invalid без бизнес-эффекта.
5. Повторяемые денежные события требуют надёжного ID операции. Определить его
   namespace по партнёрскому контракту; по умолчанию сохранить совместимость
   endpoint-scoped ID, добавить явный общий namespace для нескольких endpoint,
   если партнёр гарантирует общую уникальность. Никакого молчаливого усечения.
   Сравнивать смысловой fingerprint; тот же ID с другим лидом/суммой/типом —
   conflict, не successful duplicate. Не включать в fingerprint случайные
   транспортные поля или изменяемый порядок JSON.
6. Бизнес-эффект, идемпотентный результат, квитанция и исходящие задания
   фиксируются атомарно. Внешние HTTP-вызовы выполняются после commit через
   надёжную очередь. Повтор не должен удваивать историю, Sheets, FB/TikTok.
   Сейчас LeadEvent имеет путь TikTok; одинаковое покрытие FB не предполагать.

### Этап C. Время, атрибуция и версии настроек

1. Сохранять received_at gateway, processed_at CRM и occurred_at партнёра.
   При отсутствии времени партнёра использовать время первоначального приёма,
   помечая происхождение. Форматы ISO/Unix sec/ms задаются явно; future/invalid
   значения отклоняются по согласованному допуску.
2. Сохранять привязку персонального click/submission к карточке, боту, ссылке
   и buyer. Отложенный callback использует эту привязку, не текущую последнюю
   ссылку в чате. Не переписывать исторические события массово без сверки.
3. Endpoint configuration получает revision. Manifest/конверт фиксируют revision,
   соответствующую приёму. CRM хранит используемые старые ревизии до завершения
   очередей. Если payload подписывается партнёром, сохранять исходные байты и
   только необходимые заголовки, не пересобирать их из JSON для проверки подписи.
4. Ротация секретов с ограниченным периодом перекрытия и явным аварийным отзывом.
   Исторический delivery ID остаётся подтверждаемым; недоставленные записи не
   должны автоматически исчезать. Удаление endpoint заменить архивированием.

### Этап D. Настройка и диагностика в CRM

Отдельная понятная панель «Входящие постбэки» в настройках проекта/интеграции:
- тип обработки, партнёр, включение, секретный URL и режим direct/relay;
- mapping ID, типа/статуса, суммы, валюты, времени и ID события;
- точное правило сопоставления и таблица переходов статуса подачи;
- просмотр разбора образца без записи конверсии и без внешних триггеров;
- журнал accepted/processed/duplicate/unmatched/ambiguous/invalid/conflict/dead,
  ID доставки, причина, лид/подача/ссылка, три времени;
- контролируемая повторная обработка unmatched после исправления привязки,
  с аудитом, без нового транспортного ID и без второго бизнес-эффекта;
- состояние связи, manifest revision/age, глубина/возраст очереди и последний ACK.

Бизнес-настройки меняет admin своего проекта или superadmin. Сетевые адреса,
TLS/VPN и общий ключ остаются развёртыванием; произвольный CRM_ORIGIN из UI не
давать. Просмотр секретного URL/сырого payload ограничить администраторами;
нынешние list/receipts разрешены всем с доступом к проекту — права пересмотреть.
Секреты в логах/ошибках/экспортах маскировать. Мониторинг и алерты не должны
зависеть исключительно от доступности CRM: нужен внешний контроль приёмника.

### Этап E. Эксплуатация без лишних сервисов

Сохранить текущую SQLite-очередь, пока нагрузочный тест не покажет необходимость
другой архитектуры. Не добавлять Kafka/кластер ради самого наличия очереди.
Задать лимиты по диску/количеству/endpoint, срок хранения, алерты и backpressure.
Конкурентность отправки повышать только по измерениям; статусные события одной
подачи должны иметь контролируемый порядок, медленный проект не должен навсегда
блокировать остальные. Если сохраняем последовательную доставку — явно указать
проверенный допустимый объём и предельное время ожидания.

Определить допустимую автономность при stale manifest. Рекомендуемый старт —
сохранить fail-closed и проверить retries партнёров. Для партнёров без retries
нужна другая согласованная политика/резервирование, а не увеличение TTL вслепую.
Гарантия сохранности ограничена сохранностью диска и бэкапов; единственный
сервер с SQLite не обеспечивает нулевую потерю при гибели его диска.

## 5. Приёмочные тесты: действие и проверяемый результат

Минимальный набор фикстур: проекты S (подача) и G (гембл); два бота в каждом;
два покупателя, четыре ссылки; одинаковый Telegram ID в разных ботах/проектах;
два похожих external ID; реальные обезличенные образцы каждого партнёра.
Все тесты с бизнес-эффектом используют настоящую одноразовую PostgreSQL.
Мокать только ВНЕШНИХ покупателей, Telegram и рекламные API; не мокать receive,
record_event, сопоставление, commit и отчёт, иначе ключевые риски не проверяются.

| ID | Сценарий | Обязательная проверка |
|---|---|---|
| S01 | UUID интеграции известен, подписи/секрета нет; также старый partner route | Ноль изменений заявок/лидов, отказ на всех публичных входах |
| S02 | Ключ проекта S + lead/submission проекта G; подмена revision/type | Ноль бизнес-эффектов, отказ/invalid; нет обхода scope через payload |
| S03 | Manager читает URL/raw payload, чужой admin меняет endpoint | Отказ согласно матрице прав; разрешённый admin меняет только свой проект |
| M01 | Два лида с tracking_code; external ID 123 и 1234; один TG ID в двух ботах | ambiguous/unmatched, ни одного выбора последнего/подстрочного совпадения |
| M02 | Уникальный персональный ID из фактически отправленной ссылки или заявки | Событие ровно нужной карточке, подаче, ссылке и buyer |
| B01 | Подать тестового лида покупателю, затем принять callback approved/rejected | Конкретная подача/валидность/статус изменены по mapping; счётчики трекинга ожидаемые |
| B02 | approved пришёл раньше старого pending; повтор approved; явная корректировка | Старый статус не откатывает новый, повтор без побочных эффектов; корректировка по правилу |
| B03 | REG, FD, два разных RD одинаковой суммы; каждый отправлен трижды | В базе 1 REG, 1 FD, 2 RD; отчёт проекта/бота/ссылки/buyer даёт те же числа |
| B04 | Тот же event ID, но другая карточка/сумма/тип; ID > лимита | conflict/invalid, не duplicate-success, старое событие не переписано |
| B05 | Infinity/NaN/отрицательная/слишком большая сумма, лишняя точность, плохая валюта | Детерминированный invalid без вечного retry, без повреждения транзакции |
| T01 | 20 одновременных доставок одного UUID без partner event ID | 1 ledger, 1 бизнес-эффект, согласованный ACK всем повторам |
| T02 | 20 НОВЫХ delivery UUID с одним partner event ID | 1 бизнес-эффект, остальные duplicate; два реальных transaction ID не склеены |
| T03 | Commit CRM выполнен, ответ потерян; затем restart gateway | Повтор доставляется с тем же ID, эффект/история/исходящие задания не удваиваются |
| T04 | Ошибка между записью события и commit; reconnect/retry | Полный rollback события/ledger/заданий, затем ровно один успешный эффект |
| T05 | kill -9 gateway после принятого 200 и после claim, затем новый контейнер с тем же volume | Все принятые ID восстановлены и обработаны; нет записи done до подтверждения |

### Нагрузочный тест и критерии

Сначала измерить реальный поток и размеры payload; согласовать пик и допустимую
задержку. Предварительный профиль стенда: 1 запрос/сек 10 минут, затем 20/сек
60 секунд и восстановление нормального потока. Учитывать честные 429 и реальные
повторы тестового партнёра; не отключать лимиты глобально ради красивого результата.

Одновременно генерировать обычные старты/ответы воронок и чтение чатов на
сопоставимой копии CRM. Измерять p95/p99 ACK, end-to-end latency, очередь/диск,
CPU/RAM, DB connections/lock waits и p95 обработки входящего Telegram update.
Начальные критерии для согласования: ACK p95 < 1 сек, end-to-end p95 < 10 сек
при штатном потоке, деградация p95 новых стартов не более 10% от baseline;
ноль потерянных принятых ID, ноль лишних эффектов и deadlock, очередь после пика
возвращается к baseline в согласованный срок. Если стенд/пик иные, менять бюджет
до теста, не после неудачи. Нельзя обещать скорость по одному send_interval.

### Что не гонять ради количества

- Не повторять сотни тестов редактора/переводчика на каждом изменении gateway.
- Не считать мок ответа processed доказательством корректной записи депозита.
- Не заменять тест потери ACK тестом обычного HTTP 500.
- Не считать пропущенные PostgreSQL-тесты пройденными.
- Один полный регрессионный прогон после интеграции; в итерациях — конкретный
  упавший тест, профильная группа и проверки затронутого контракта.

## 6. Порядок запуска и передача между диалогами

1. Зафиксировать контракты партнёров и собрать одноразовый стенд двух компонентов
   с реальной PostgreSQL. Прогнать имеющиеся три relay-теста, не заменяя их моками.
2. Исправить P1: старый публичный вход, обе бизнес-ветки, точное сопоставление,
   дедупликацию, время/атрибуцию и валидацию. Затем revisions/reprocess/мониторинг.
3. Выполнить матрицу выше и нагрузочную проверку. Подготовить отчёт с фактическими
   результатами, миграциями, известными ограничениями и проверенными payload.
4. Основной сервер: резервная копия с пробным восстановлением; миграции;
   интеграция выключена; приватный listener через VPN, запрет внутренних путей
   снаружи, без доступа приёмника к БД/Redis/Telegram-сессиям.
5. Отдельный сервер: только новый подписанный/контрольный по checksum пакет
   gateway, свой compose/volume, TLS, firewall, NTP, бэкапы и внешний мониторинг.
   Старый handoff-архив от 03.11 не объявлять автоматически готовым после будущих
   доработок: пересобрать и указать совместимые версии протокола обеих сторон.
6. Согласованные тестовые проекты: один submission, один gambling. Проверить
   всю цепочку с тестовым покупателем/игроком, не создавать события реальным лидам.
7. После допуска включить ограниченный список проектов, перевести одного
   партнёра каждой категории и наблюдать минимум полный цикл его уведомлений
   с переходом суток. Сверить ID/счётчики с выгрузкой партнёра.
8. Остальных переводить поэтапно. Старые прямые адреса отключать только после
   сверки и переноса отправителей; старый partner-status route учитывать отдельно.
9. Откат: остановить расширение и новый приём выбранной интеграции, сохранить
   очереди/ledger, согласовать старый путь. Не удалять volume, не менять ID
   pending, не выполнять разрушительный downgrade и не переигрывать всё подряд.

Артефакты для основного диалога: main-server инструкция, миграции, список
проектов/партнёров и протокол тестов. Для отдельного диалога: gateway-only пакет,
gateway-server инструкция, согласованные VPN/порт/протокол, ключ безопасным
каналом. Никаких CRM .env/базы/ботов в пакете отдельного сервера.

## 8. Входные данные перед реализацией

- Контракты/обезличенные примеры всех активных покупателей и гембл-партнёров.
- Для подачи: какие статусы и теги должны меняться, что считать валидным лидом,
  как обрабатывать отмену/корректировку. Не подменять выбранное правило «по тегам».
- Для гембла: где выдаётся персональный sub ID, различает ли партнёр FD/RD,
  реальные event/transaction IDs, валюты, повторы/исправления и время события.
- Пик запросов, допустимый простой/задержка, retries и ожидаемый ответ партнёра.
- Доступность тестового окружения PostgreSQL/Docker и тестовые интеграции.

Без этого можно подготовить общий механизм, но нельзя честно принять конкретную
партнёрскую интеграцию как готовую к живому трафику.
