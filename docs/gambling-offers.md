# Гембл-офферы и персональные ссылки

## Границы обновления

Только основной сервер CRM. Отдельный postback gateway остаётся отдельным
артефактом: не запускать его compose/nginx/очередь на основном сервере.
Протокол relay не меняется, персональные привязки остаются только в CRM.
Новые endpoint создаются **выключенными**. Выкладка кода не означает разрешения
включать живой трафик или отправлять тестовые конверсии реальным лидам.

**Сокращение ссылок: Будет добавлено позже.** Сейчас ссылки полные,
без промежуточного перенаправления через Сферу.

## Настройка техником

1. В гембл-проекте открыть Настройки → Гембл-офферы.
2. При необходимости на вкладке «Условия выплат» создать программу: ПП, ставка
   за квалифицированный FD, валюта вознаграждения, минимальная сумма и валюта
   депозита, поле квалификации и значения подтверждения/отказа.
   Прочие условия ПП записываются примечанием, НЕ исполняемым кодом/формулой.
   Условия, которые нельзя проверить по сумме/валюте/флагу, проверяет администратор.
   Если есть примечание, но не настроен подтверждающий флаг ПП, FD автоматически
   остаётся на проверке: свободный текст не трактуется как выполненное условие.
3. Выбрать период (день, неделя пн–вс, месяц, заданные даты) и часовой пояс.
   По умолчанию Europe/Moscow. Последний день заданного диапазона включён.
   При групповом подсчёте назначить **одну общую программу** офферам той же ПП.
   Похожие названия сами по себе программы не объединяют. Проекты не смешиваются.
4. На вкладке «Офферы» указать название, ПП, полную исходную ссылку и условия
   выплаты. Для обычной ссылки оставить «Использовать постбэки» выключенным.
5. Для постбэков указать параметр исходящей ссылки (например `sub1`) и правила
   входящего запроса: где возвращается идентификатор, тип REG/FD/RD, сумма,
   валюта, ID операции, время события и необязательный Player ID. Обозначения
   партнёра вроде `ftd` можно сопоставить с FD. REG/FD/RD распознаются штатно.
6. Сохранить оффер. В форме появится **полный адрес приёма с доменом**.
   Новый endpoint выключен. Проверить контракт без записи в
   Настройки → Партнёры → Получение постбэков, согласовать тест и только затем
   включить приём. Внешний домен берётся из существующей настройки relay,
   менять BASE_URL самой CRM для этого нельзя.
7. В конструкторе открыть нужную **черновую версию** → Настройки воронки →
   Оффер, выбрать и отдельно сохранить оффер. В текст/подпись или URL кнопки
   вставить `{{offer_link}}`. Отдельного сокращателя нет.
8. Проверить и опубликовать версию. Не настроенный/недоступный оффер блокирует
   публикацию, если используется переменная. При ошибке во время исполнения
   сообщение не отправляется с буквальным `{{offer_link}}`.

Опубликованная версия не меняет оффер через этот интерфейс. Новый черновик
того же проекта наследует выбор; копия в другой проект — нет. Старые версии,
в которых нет переменной, не требуют оффер и не переписываются.

## Персонализация и сохранность ссылок

- Первая подстановка создаёт случайный непрогнозируемый токен, связанный с
  карточкой, оффером и конкретным прохождением. В URL не подставляется CRM UUID.
- В пределах одного прохождения повторная подстановка выдаёт ту же ссылку,
  в том числе в подписи и кнопках. Полноценный новый запуск после завершения
  или сброса получает отдельный ключ прохождения и новую ссылку. Обычный
  повторный /start в незавершённой воронке ключ не меняет. Старые привязки
  не удаляются; у уже запущенных состояний без нового ключа используется ID состояния.
- Для оффера с постбэками заданный query-параметр заменяется одним токеном.
  Остальные параметры сохраняются, включая повторяющиеся ключи, `%20`, `+`,
  пустые значения и fragment. Сами адреса никогда не загружаются сервером CRM.
- Без постбэков выдаётся исходная строка URL без нормализации и новых параметров.
- Адрес и рекламная атрибуция выданной ссылки неизменяемы. Правка оффера влияет
  на новые выдачи, но не переписывает отправленные сообщения или ранее выданные
  ссылки. Смена ПП у оффера с выданными ссылками запрещена: нужен новый оффер.
- Изменение правил разбора создаёт новый выключенный endpoint. Старый endpoint
  не отключается автоматически и продолжает принимать старые ссылки.
  После согласования отдельно обновить URL у партнёра. Ротация/архивирование
  старого адреса — явное действие администратора, не часть сохранения оффера.

## Приём и повторы

Партнёр возвращает токен в согласованном поле. CRM проверяет endpoint, проект,
оффер и конкретную карточку. Событие получает источник, бота, баера и версию
воронки из сохранённой выдачи, а не из текущих изменённых полей чата.

REG и FD имеют по одному первому факту на карточку/оффер. Повтор с теми же
данными не создаёт второе событие или вознаграждение; противоречащая сумма/
валюта — conflict. Для RD нужен уникальный ID операции: два разных RD с
одинаковой суммой допустимы, один RD с повторным ID — нет.

После первого надёжного токена Player ID связывается в namespace оффера.
Последующие player-only события используют эту точную привязку и её атрибуцию.
Player ID нельзя молча переназначить другому лиду. Отсутствующая/неоднозначная
идентификация сохраняется в существующем журнале квитанций, не угадывается по
рекламной ссылке, имени или «последнему» лиду. Без поддержки возврата токена
или предварительно подтверждённой точной привязки автоматической сверки нет.

Неизвестный результат квалификации считается ожидающим проверки, не отказом
и не подтверждением. Если затем пришло подтверждение **того же FD с теми же
суммой/валютой/временем**, ожидающая квалификация может подтвердиться один раз
без создания второго FD. Решение администратора и окончательный отказ таким
повтором не перезаписываются. Сырые входящие запросы остаются в квитанциях.

## Версии выплат: на дату FD

Согласованное правило: версия условий выбирается **по фактическому времени FD**,
не по времени выдачи ссылки и не по приходу позднего постбэка.

CRM сохраняет историю назначения программы офферу и неизменяемые версии её
условий. Сохранение новой версии действует на последующие времена событий;
задним числом дату начала не подделываем. Зафиксированный у FD выбор версии
последующими правками не заменяется. Если на дату FD не было условий, доход
неизвестен, а не равен нулю.

Для автоматического расчёта требуется время FD от партнёра. Без него событие
сохраняется с временем получения, но версия выплаты не угадывается; дата в
карточке помечается как время получения. Администратор может указать фактическое
время при проверке. Это явная корректировка канонической даты события с аудитом,
без повторной отправки рекламной конверсии. Менеджер этого делать не может.

Депозит и вознаграждение — разные сущности и валюты. Автоматической валютной
конвертации нет. Если порог задан в USD, а депозит пришёл в EUR, без надёжной
проверки квалификации это ручной разбор, не сравнение несопоставимых сумм.
Ручные FD также требуют административной проверки для выплаты.

### Мотивационная сетка

- Ставка «только сверх порога»: при пороге 10 первые десять FD остаются по
  базовой ставке, начиная с одиннадцатого действует повышение.
- «Пересчёт периода»: при достижении порога для соответствующей версии применяется
  её повышенная ставка. Каждая версия действует по своим закреплённым правилам;
  новая версия сама по себе не заменяет ставки у старых FD.
- Фиксированный бонус выдаётся один раз за достижение соответствующего порога.
  Несколько разных порогов с бонусами складываются. Бонус относится к версии
  условий того FD, на котором достигнут порог, а не дублируется для каждой версии.
- Счётчик программы не обнуляется при выпуске новой ставки: квалифицированные FD
  учитываются внутри расчётного периода по той же программе и области подсчёта.
- В групповой программе учитываются все назначенные ей офферы той же ПП в проекте.
  В режиме по офферу счётчик отдельный для каждого оффера.
- Время определяет порядок FD; при равных метках используется стабильный UUID
  факта. Поздний FD может уточнить достижение порога периода. Это новая информация,
  а не переписывание финансовых условий. Исходные факты и версии сохраняются.

Вкладка «Вознаграждение» показывает **расчёт**, а не банковский факт выплаты ПП.
Это не платёжная система и не расчёт прибыли за вычетом расходов. Для сверки
выбрать дату внутри нужного периода и при необходимости программу выплат. Непроверенные FD и FD без условий показаны
отдельно. Решение по квалификации фиксируется с администратором, временем,
основанием и предыдущими данными; второе решение поверх первого не принимается.

## Карточка и доступ

Карточка показывает только REG, FD, RD, даты и суммы. Общая сумма депозитов
отдельная для каждой валюты; неизвестная сумма не становится `0.00`.
Постранично доступны более ранние события. Ответ `/leads/{id}/deposit-summary`
сформирован белым списком: без сырых payload, ставок, бонусов, версий выплат,
расчётного дохода и условий ПП. Финансовые API доступны только admin/super_admin
с доступом к проекту. Менеджеру/оператору/баеру они возвращают 403, а не просто
скрывают поля в интерфейсе.

Без постбэков событие можно записать вручную с выбором оффера и даты. Подмена
ссылок не требуется. В карточке и новом обзоре трекинга неполные данные помечены;
нулевые REG/FD/RD и зависящая от них конверсия при неизвестном покрытии не
выдаются как подтверждённый нулевой результат. Сырые legacy-счётчики остаются
числом зафиксированных событий, не гарантией полной истории ПП. Импорт событий
из внешних файлов — отдельная несогласованная доработка.

## Старая база и выкладка

Миграция `20261106_0096` после `20261105_0095`: новые таблицы и nullable offer_id
у версии воронки. Не запускает DML по старым лидам/событиям, не создаёт офферы,
не пересчитывает источники, не начисляет исторический доход. Старые `{{lead_id}}`
и точные postback-привязки остаются совместимы. Появление новой персональной
ссылки старому лиду возможно только при предусмотренной следующей отправке,
а не массовым переотправлением истории.

1. До выкладки проверить свежий бэкап и его восстановление. Полная копия базы
   нужна на хосте с достаточным диском. Здесь проведён тест добавочной миграции
   на изолированной структуре с контрольными старыми данными, НЕ восстановление
   полного пользовательского бэкапа на 632 MiB: свободного локального диска мало.
2. На копии выполнить upgrade head; сверить количество/ID старых чатов, лидов,
   событий, источники, опубликованные версии и сохранность старых callback.
3. На основном сервере применять миграцию перед стартом нового API/jobs worker,
   в окно низкой нагрузки. lock_timeout 5 секунд: ошибка должна откатить DDL,
   а не стать поводом удалять данные. Не обновлять только frontend.
4. Офферы и endpoints остаются opt-in. Сначала согласованный тестовый проект,
   затем явное включение конкретного оффера/версии и живой интеграции.
5. При откате кода новые таблицы не удалять: downgrade намеренно запрещён.
   Старый код не понимает offer_token и {{offer_link}}: сначала остановить
   новые офферные воронки и согласованно сохранить входящие постбэки в очереди
   gateway. Нельзя просто откатить обработчик при работающем новом трафике.

Локальные контрактные проверки не означают, что конкретная ПП проверена.
Для её запуска нужен обезличенный реальный пример и согласованный smoke-test.
