# Постбэки: инструкция настройки

Актуальная реализация: протокол приёмника 2, миграция CRM `20261103_0094`.
Путь в CRM: **Документация → Постбэки**. Настройка доступна admin своего проекта
и superadmin: **Настройки → Партнёры**.

## Отправка и получение — разные направления

**Подача:** во вкладке «Отправка покупателю» указываются URL покупателя,
авторизация, тело запроса и правила разбора ответа. Домен получателя виден над
формой. Сам запрос, как и раньше, отправляется основным сервером CRM.

**Гембл:** вкладка «Получение постбэков» работает без исходящей интеграции.
Отправка покупателю в интерфейсе гембл-проекта скрыта. Для подачи получение
обратных статусов настраивается независимо от отправки.

Домен вверху получения — НАШ адрес приёмника. Полный секретный URL endpoint
копируется из его карточки и передаётся партнёру. Это не URL покупателя.
Домен поступает из серверной конфигурации, техник не редактирует его в форме.
Если relay включён, а внешний домен не указан, видны предупреждение и фактический
прямой адрес CRM. Не выдавать такой адрес за уже готовый отдельный сервер.

## REG / FD / RD

1. Создать endpoint с обработкой «Событие лида».
2. В «Как найти лида» выбрать точный идентификатор. Предпочтительно передавать
   партнёру CRM Lead ID и получать его обратно, например параметром sub_id.
   Для собственного Player ID партнёра нужна сохранённая привязка.
3. Указать параметр ID операции event_id и оставить требование уникальности
   включённым. Два разных редепозита должны иметь разные ID операций, даже
   при одинаковой сумме. ID игрока не является ID операции. Для RD отсутствие
   ID операции отклоняется даже при выключенном checkbox.
4. Если тип приходит в параметре, указать его имя. Поддержаны reg/registration,
   fd/first_deposit/deposit, rd/redeposit; остальные названия задаются алиасами,
   например `{"signup":"registration","ftd":"deposit"}`.
5. Настроить сумму, валюту, время. Деньги должны быть конечными, неотрицательными,
   до 9999999999999999.99 и не более двух десятичных знаков. ISO-время должно
   содержать пояс; Unix seconds и milliseconds выбираются отдельно.
6. Для регистрации, которая возвращает одновременно наш ID и Player ID, указать
   «Параметр Player ID для последующей привязки». После успешной регистрации
   последующие FD/RD смогут находить эту карточку по Player ID.
7. Если используются разные endpoint одного партнёра, указать у них одинаковое
   «Общее пространство ID событий». Оно объединяет дедупликацию и привязки ID
   внутри проекта. Не объединять независимых партнёров с пересекающимися ID.

Пример настройки: идентификатор lead_id, параметр идентификатора sub_id,
параметр типа event, ID операции transaction_id, сумма amount, валюта currency,
время occurred_at/iso. Пример тела (это синтетический образец, не договорённость
с конкретным партнёром):

```json
{"sub_id":"<UUID карточки CRM>","event":"fd","transaction_id":"payment-1001","amount":"20.00","currency":"USD","occurred_at":"2026-11-04T12:00:00+03:00"}
```

## Персональная ссылка и источник

В тексте сообщения или URL inline-кнопки воронки поддерживается
`https://partner.example/?sub_id={{lead_id}}`. При рендере персональной ссылки
фиксируется первоначальная атрибуция карточки. Партнёр обязан вернуть этот UUID;
в mapping выбирается CRM Lead ID, а не Click ID только потому, что параметр
называется sub_id. Дополнительный namespace не превращает рекламную ссылку в
личный ID пользователя.

Для уже существующего Player/Click ID можно открыть «Привязка внешнего ID к
карточке» в endpoint. Привязать один ID другому лиду без ошибки конфликта нельзя.
Более одного совпадения по Telegram ID — ambiguous. Поиск подстроки во всём
JSON и выбор последнего лида рекламного источника больше не используются.
У старых данных без исторической привязки восстановить исходную ссылку из
одного callback не всегда возможно; система не должна её выдумывать.

## Обратный статус подачи

1. Сначала создать исходящую интеграцию покупателя и проверить подачу тестового
   лида. Сохраняемый внешний ID берётся из parsed.external_id ответа.
2. В получении выбрать «Обратный статус подачи» и нужного покупателя.
3. Лучше использовать CRM Submission ID. Точный External submission ID также
   поддержан, включая старые ответы с parsed.external_id. При нескольких подачах
   одного лида неоднозначный lead_id не заменяет ID конкретной подачи.
4. Указать поле статуса и mapping на существующие коды CRM, например:

```json
{"accepted":"submitted","approved":"qualified","rejected":"lost"}
```

5. Задать разрешённые переходы после первого callback:

```json
{"accepted":["approved","rejected"],"approved":["rejected"]}
```

Время callback партнёра рекомендуется обязательно: запоздавший статус не
откатывает более новый. Отмена/корректировка должна быть разрешена в переходах.
При отсутствии времени порядок определяется временем приёма, а не догадкой о
времени события. Статус HTTP-ответа исходящей подачи не считается временем
последнего callback. Повтор одного ID не выполняет действия второй раз.
is_valid устанавливается существующим правилом qualified/lost. VIP и теги
не присваиваются неявно, подсчёт целевых карточек по тегам/статусам не меняется.

## Проверка перед переводом партнёра

- «Проверить без записи» разбирает образец и ищет карточку/подачу без конверсии,
  квитанции, привязок и отправок в Google Sheets/рекламные API. Также проверяются
  повтор/конфликт ID операции, существование статуса CRM, разрешённый переход и
  конфликт автоматической привязки. Это снимок состояния: параллельный реальный
  callback может изменить результат после проверки.
- После этого нужен согласованный тестовый callback на тестовую карточку и
  сверка результата с партнёром. Старые образцы из тестов не доказывают
  совместимость с изменившимся API покупателя.
- Обычный ответ gateway — JSON accepted + delivery_id. Если партнёр требует
  статический текст, например OK, заполнить «Текст ответа партнёру». Положительный
  ответ приёмника означает сохранение на диск, не успешную конверсию.
- При недоступности/переполнении возвращается 503, при rate limit — 429.
  Партнёр обязан повторять такие запросы. Произвольные форматы подписи партнёров
  автоматически не угадываются: требуется его конкретный контракт.

## Журнал и повторный разбор

- processed — применён бизнес-эффект; duplicate — повтор без второго эффекта.
- unmatched — нет точной привязки; ambiguous — несколько совпадений.
- invalid — неверные обязательные поля/формат; conflict — разные данные под
  одним ID или запрещённый переход; stale — старое уведомление о статусе.

После исправления привязки или mapping можно повторно разобрать unmatched,
ambiguous, invalid. Использование текущей новой версии настроек подтверждается
явно. Исходный payload сохраняется, предыдущая попытка и администратор записаны
в attempt_log. Успешные и конфликтные записи этим действием не переигрываются.

Показываются время события и время приёма; в API доступны также processed_at
и revision. Событие получает время партнёра либо первоначального приёма gateway,
но не новый день из-за долгой очереди. Существующие lifecycle-отчёты используют
UTC-границы; этот апдейт не переводит исторические отчёты молча на другой пояс.

Google Sheets и Facebook-действия новых обратных статусов идут из durable
followup-очереди после commit, TikTok lifecycle — через существующий DB outbox.
Неопределённая внешняя доставка переводится в «Требуют сверки», не повторяется
вслепую: сначала проверить внешнюю систему, затем подтвердить выполнение или
явно повторить. Это важно для append в Google Sheets: внешний сервис без своего
idempotency key не позволяет гарантировать exactly-once после потери ответа.
Очередь followups обслуживает jobs worker с новым cron; его обязательно обновить.
Раз в минуту он проверяет heartbeat (120 сек), ожидание (300 сек), dead и свободное
место gateway (512 МиБ); пороги POSTBACK_RELAY_ALERT_* задаются на основном сервере.
Оповещения идут через существующие operational alerts с защитой от спама.
При полной остановке CRM нужен независимый внешний мониторинг приёмника.

## Совместимость и отключение старых входов

Старые исходящие интеграции и URL не отключаются при обновлении или создании
endpoint. У новых исходящих интеграций незащищённый старый status-route закрыт
по умолчанию. После переноса конкретного старого покупателя нажать «Закрыть
старый адрес обратных статусов». Когда перенесены все:

```dotenv
LEGACY_PARTNER_POSTBACKS_ENABLED=false
```

Это отдельный маршрут от /pb. Для отключения прямых /pb после переноса ВСЕХ
отправителей на gateway используется POSTBACK_DIRECT_ENABLED=false. До окончания
переноса доступность старого незащищённого маршрута — известный риск совместимости,
а не новая гарантия безопасности. Не считать миграцию завершённой, пока входы
не инвентаризированы и не закрыты.

Ротация секрета по умолчанию даёт 3600 сек перекрытия, управляется
POSTBACK_ROTATION_GRACE_SECONDS. Ранее принятые события с frozen revision могут
доставиться позже окончания перекрытия. Аварийный отзыв revoke_old=true запрещает
старые ревизии, включая pending; подтверждение уже выполненного delivery UUID
остаётся возможным. Непринятые/отозванные записи не исчезают, их надо разобрать.

Удаление endpoint — архивирование с сохранением журнала/дедупликации. «Показывать
архив» открывает старый журнал; восстановление возвращает endpoint ВЫКЛЮЧЕННЫМ,
включение подтверждается отдельно. Не архивировать endpoint с pending без
согласованного плана: приём/доставка для него останавливаются.

## Развёртывание

Основной сервер: docs/postback-relay-main-server.md. Отдельный сервер:
docs/postback-relay-gateway-server.md. Сначала обновить CRM до 0094 и jobs worker,
затем gateway. Новый протокол совместим со старыми клиентами, но гарантии frozen
revision/received_at появляются только у gateway протокола 2. Его старую очередь
не удалять и не переписывать; старые конверты доставляются как раньше.

Не разворачивать gateway на основном сервере и не копировать туда-сюда CRM .env,
Telegram-сессии, токены ботов или базу. Подробная инструкция также включена в
страницу документации CRM. Это обновление не выполняет никаких live-тестов,
изменений DNS, автоматического переноса партнёров или включения живого трафика.
